# Distributed factory

The same factory on several machines of the person in charge, coordinated through a private GitHub repository.

- `src/machine.ts` and `src/coord/`: the distributed factory (`docs/adr/0007-fabrica-distribuida.md`), off unless the factory file has `distributed` (strict: `repository` `owner/name`, `heartbeatSeconds` at least 30, default 60, `leaseMinutes` at least 2 and three heartbeats, default 10, optional `machine`). `machineIdentity` keeps the machine's id in kv `machine:id` (name from `machine` or the host); `machineCapabilities` declares only `platform`, `box` and `engines`. `protocol.ts` (`CoordApi`, `CoordConflict`, `memoryCoord`) holds `claimJob` (create `claims/<job>`; a closing record, an unreadable claim or an expired holder is taken over only from the tip read, an expired holder returned as `takenFrom`), `stillHolds` (false for a closing record), `releaseJob` (a compare-and-swap of the claim to a closing record `{job, machine, name, at, released: true, status}`, never a delete, since GitHub deletes refs with no expected tip), `readClaimOf`, `probeCoord` (creates `probe/<id>`, checks that creating it again and moving it from a stale sha give `CoordConflict`, then deletes it), `heartbeat` (`machines/<id>`, public fields only) and `listMachines`; `github.ts` (`githubCoord`) maps it to refs `refs/heads/zero-coord/*` on empty-tree commits of the private coordination repository, 422 becoming `CoordConflict`, never Actions. `coordPass` (`pass.ts`, the daemon's `coordinate`, at most every `heartbeatSeconds`, the meter's `coord` pass, skipped during `githubHalt`, off in `once` runs unless `DaemonOptions.coord` is injected) probes the repository first, once per `distributed.repository` and a failed probe again at most once an hour (`PROBE_RETRY_MS`), keeping `{repository, at, ok, problem?}` in kv `coord:probe`, then beats and stores the list in kv `coord:machines`, which `factoryStatus` gives as `FactoryStatus.machines` only with `distributed`, shown as the `Máquinas:` block (`machineLine` in `src/format.ts`) of `formatStatus` and the panel summary. `joinFactory` in `app.ts` (`zero unirse <owner/repo>`, an injectable `CoordRepoCheck` and `JoinDeps`: coord, cloner, platform, signal) writes `distributed.repository` through `editConfig` only for a private repository it can read; without a repository, or with an invalid name, a public one or an unreadable one it explains how to create it (`coordRepoHelp`: `gh repo create <owner/repo> --private --add-readme`, since GitHub refuses the records in a repository with no commits) and zero itself creates nothing. `zero repo crear <nombre> --coordinacion` (`createProject` with `coordination`, see `docs/agents/core.md`) creates that repository private with a first commit (the coordination adapter needs one), after the owner's confirmation, and joins it through `joinFactory` without cloning it or adding a line; it refuses `--publico`. Once joined, `joinLines` probes the repository when no passed probe is kept (`probeOnce`, a failed one at once), runs `linesPass` once and tells what was cloned, what this machine does not take and what failed; a problem there (a pause, no token, a failed probe) is only told, the machine stays joined and the daemon tries again. Records read back are validated strictly (ids `[A-Za-z0-9-]`, ISO times, names without control characters). `coordReady` is true only with `distributed` and a passed probe of its current repository; the runner relies on the protocol only then. Only while `coordReady` (and in `once` runs only with an injected `DaemonOptions.coord`), the daemon's queued loop calls `claimJob` right before `runJob` and skips a job it did not get (it stays queued, never failed; a claim error or a GitHub pause also skips it), passes the runner a `holds` dep (`stillHolds`, an unreachable repository counting as still held) and releases with `releaseJob` when `runJob` returns a final status, or `queued` after a shutdown; an andon, a quota stop, a question or a lost job keep the claim as it is. The runner asks `holds` (`ensureHolds`) before the conflict agents, spec, every build attempt, each writing agent, verify, each review, the approvals and integrate; a false answer throws `Interrupted("lost")`, which ends the job through `finalizeJob` as stopped with `LOST_TO_ANOTHER` ("Lo retomó otra máquina de la fábrica."), without integrating. `endedElsewhere` (`src/line/finish.ts`: that reason, `TAKEN_BY_ANOTHER` and `endedOn(name)`) makes `report` in `src/intake/github.ts` (GitHub, Linear, Jira) say nothing and the issue comments pass skip the job. The shared queue (`src/coord/queue.ts`, `queuePass`, run by `coordPass` after the heartbeat only while `coordReady`) lists `claims/` once and ends, through `finalizeJob` with that status and `endedOn(name)` ("Lo terminó la máquina <nombre>."), every local queued job whose claim is another machine's closing record of `delivered`, `failed` or `stopped` (`finished`); imports every `queue/<job>` record that reads strictly (`readQueueRecord`: id `[A-Za-z0-9-]` matching its ref, kind, request up to 100 000 characters, priority, a plain `source` of a known kind, ISO `createdAt`, `needs {box, engines}`) whose line exists here, whose id is not a local job and whose claim is not finished, as a queued job with the same id and `createdAt` (`Store.createJob` takes both) and the local `limits.usdPerJob`; and publishes every local queued job not yet published or imported (kv `coord:job:<id>` `{origin: published|imported, needs}`) as `queue/<job>` `{id, line, kind, request (scrubLocal), priority, source?, createdAt, needs}`, `needs.box` being a job started in the box or `isolation: container` with the box ready, and `needs.engines` the first engine of every agent station (`primaryEngines`). A job with a source first creates `sources/<sourceKey>` (a hash of the origin, the same on every machine; a package's requests are keyed by their job) naming it (`claimSource`); when the ref names another job, the local one ends stopped with `TAKEN_BY_ANOTHER` ("Lo tomó otra máquina de la fábrica.") unpublished, and its intake state (`issue:`, `linear-issue:`, `jira:` keys) is repointed at that job. Before claiming, the daemon skips an imported job whose `needs` this machine cannot meet (`canTake`: the box ready when asked, every engine in its stations' chains) and an imported job whose line is gone here (never failed), and claims with `keepFinished`, so another machine's closing record of an ended job is not taken over: the local copy ends with that status and `endedOn(name)` instead. While `coordReady`, the daemon also gives the runner a `pushProgress` dep (`src/coord/progress.ts`): at three checkpoints (after the spec is saved, after each stage that passes verify and right before integrate, `checkpointPush` in the runner) it checks `stillHolds` (false: `lost`, no `git push`; an unreachable repository skips the push), publishes the work copy and pushes `refs/heads/<branch>` from the line's repository to its `origin` with `--force-with-lease=refs/heads/<branch>:<sha>`, the sha being the last one this machine pushed (kv `coord:pushed:<job>`; none means the branch must not exist there). A push refused by the lease means someone else moved the branch: `lost`, and the job ends as `LOST_TO_ANOTHER`; a line without `origin` or any other push failure only logs and goes on. After a push it stores the sha and writes `progress/<job>` (`progressRef`) `{job, machine, checkpoint, stagesDone, branch, base, sha, title, spec, attempt, at}` by compare-and-swap from the tip read (create when missing; a conflict is `lost`). A job cut short by a shutdown on purpose pushes what is committed the same way before `runJob` returns it to the queue, and the daemon releases its claim right after, both before the daemon lock is released. Right after a claim, the daemon calls `resumeProgress` (`src/coord/progress.ts`) whenever `progress/<job>` names another machine or the claim came with `takenFrom`: it reads progress strictly (`readProgress`: the job's id, a `COORD_ID` machine, checkpoint `none`, `spec` or `review`, `stagesDone` up to `MAX_STAGES`, branch and base of plain ref characters with no `..` or leading `-`, a 40-hex sha, a spec that passes `SpecSchema` and `specProblems`), removes the job's old work copy, fetches the branch from the line's `origin`, sets it at progress's sha (its base must resolve here) and puts the job at that checkpoint with its spec, title, stagesDone, branch, base and attempt, so the runner skips what was pushed; an invalid or missing progress or a branch that cannot be brought starts the job from scratch (checkpoint `none`, the local branch deleted). Either way kv `coord:pushed:<job>` becomes the branch's tip on the remote, the lease of this machine's next push. A machine that comes back after another took its job over finds `stillHolds` false at its next station and ends as `LOST_TO_ANOTHER`, with no push, integration or comment.
- `src/coord/spend.ts`: the spend of a distributed factory. `spendPass` (called by `coordPass` after the heartbeat and before the queue, only while `coordReady`) keeps every other machine's valid `spend/<id>` in kv `coord:spend`, alive or down, and writes its own (`ownSpend`) only when it says something new; slots that only grew old are no change, and a machine that spent nothing writes nothing. `SpendRecord` (`readSpendRecord` in `protocol.ts`, strict, only the known fields): `slots`, the agent calls of the last 48 hours in 15-minute slots by the call's start, engine, billing (`api`, `subscription` or `unknown`, as `callBilling` tells it on the machine that made them) and `idle` (`isIdleCall` in `src/telemetry/metrics.ts`); and `jobs`, what each unfinished job, or one finished in those 48 hours, was charged there; and `plans`, the latest subscription reading of each engine there (`planReadings`; `planWindows` keeps the valid windows), absent with none. Never prompts, paths or texts, and never what other machines spent. `src/budget.ts` adds it, only with `distributed`: `billedToday` the `api` slots of the day (also pausing an engine with no reading here yet), `estimatedUsd` every slot, `scoutSpent` (with its `config` argument) the idle slots not on a subscription and `jobBilledUsd` the job's charges. A slot that crosses the start of the period counts whole. `billedUsd` and the month's figures stay this machine's own. The plan is one per account: `engineBudget` uses the newest of its own subscription reading and the others' (`othersPlans`, ignoring one dated ahead of this clock or over 8 days old), so a window used up or past `reservePercent` on one machine pauses the engine on all; for an engine paid per use here they are ignored, and with no reading here they can only pause it (billing stays `unknown`, the dollar caps stay). How a call is billed comes only from this machine's readings. `BudgetState.shared`, set only with spend of today or plan readings of other machines, makes `budgetLine` and the panel say the budget is the whole factory's.
- `src/coord/status.ts`: where every machine's jobs stand. `statusPass` (called by `coordPass` after the queue, only while `coordReady`, with the claims `queuePass` read) keeps every other machine's valid `status/<id>`, alive or down, and the claims of those jobs and of this machine's unfinished ones in kv `coord:status` (`readStatus`), and writes its own (`ownStatus`) only when it says something new. `StatusRecord` (`readStatusRecord` in `protocol.ts`, strict, only the known fields, no control characters): `jobs`, the unfinished ones and the last 10 finished in 7 days, except those that ended because another machine has them (`endedElsewhere`), with id, line, title, status, station, attempt, stage, priority, times and, while waiting, the question (kind, text, askedAt, expiresAt, onTimeout); and `proposals`, the pending ones (`proposalsElsewhere` in `app.ts`). Every text goes whole through `scrubLocal` for the line's repository and for ZERO_HOME before any cut. `factoryView` in `app.ts` puts the local jobs and the others' together, each id once: the copy of the machine that holds its claim or left its closing record; that machine with the claim's word when it told nothing of the job yet; and with no such claim the copy at work, then the queued one, then the finished one, this machine's first. A `FactoryJob` names its `machine` (`alive` as the last pass saw it) and carries `local`, the full record, only when this machine's copy is the one that counts. It is undefined without `coordReady` or while no other machine is known, and then every screen is the one of a single machine. `FactoryStatus.jobs` (the unfinished ones and those finished in 7 days) makes `formatStatus` and the panel's summary list every machine's jobs with ` · en <máquina>` (`machineNote`, saying when it is down); `running`, `queued`, `waiting` and `recent` stay this machine's own. `jobText` (`zero status <id>` and `zero_status`), `requestsView` (its `away` rows) and the panel's `/job/<id>` (`jobElsewhere`, `factoryJobPage`) show another machine's job with its question, whose answer is the only action on it; its texts are escaped and told as data.
- `src/coord/outbox.ts` and `src/coord/actions.ts`: asking, answering and deciding from any machine. Nothing is sent at once: the CLI, the chat and the panel leave an entry in kv `coord:outbox:<id>` (`OutboxEntry`), and `outboxPass`, the last step of `coordPass` (so only while `coordReady`, and after a GitHub pause), publishes each one once and keeps what came of it, shown as `FactoryStatus.sent` (`sentLine`, the `Para otras máquinas:` block of `formatStatus` and the panel's summary, and `zero status <id>`) for a day after it ended. `answerAnywhere` (`zero approve`, `zero_answer`, both answer forms of the panel) answers a local job with `answer` and one that `jobElsewhere` gives with a decision; `decideProposal` (`zero proposals`, `zero_proposal_decide`, the panel) does the same with a proposal of `proposalsElsewhere`. A decision is `decisions/<decisionKey>` (`readDecisionRecord`, strict, only the known fields; the note goes through `scrubLocal`), one ref per question (the job and its `askedAt`) or proposal, so the first one created wins; an entry whose question is over in the view just read, or whose ref is another decision's, ends `late` ("ya se había respondido"), and one on its way refuses a second from the same machine. `decisionsPass`, after the queue and before the status, applies those whose `to` is this machine with `answerJob`, `approveProposal` or `rejectProposal`, only while that job waits on that same question and no other machine holds its claim, or while the proposal is pending; whatever came of them, they are deleted after the status says where the job stands. A record that does not read has no effect, and is deleted when it stands where a decision for this machine would go. Over the remote chat, approving the protected paths of another machine's job (by the question of the view; `askedAt` ties the held action to it) or deciding its proposal is held as a local one, and enters the outbox only when confirmed. `requestAnywhere` (`zero request`, `zero_request`, the panel's forms, which offer `requestLines`) sends a request for a line that is published but not here (`publishedElsewhere`, from kv `coord:lines`, which `linesPass` writes) as a `queue/` record with the line's needs and no local job; `factoryView` tells of it until a machine does.
- `src/coord/lines.ts`: the lines of a distributed factory. `linesPass` runs as the daemon's own background pass (`shareLines`, at most every `heartbeatSeconds`, through `protocol()` so only while `coordReady` and in `once` runs only with an injected `DaemonOptions.coord`, the meter's `coord` pass, skipped during `githubHalt`), never inside `coordPass`, so a slow clone holds up neither the heartbeat nor jobs; a shutdown cuts it and it is awaited in the `finally`. It publishes each local line whose `remote` is github.com itself as `lines/<name>` (`lineRef`; `LineRecord`: name, repository `account/name`, baseBranch, setup, verify, verifyTimeoutMinutes, integrate, autoMerge, needs `{engines: primaryEngines, platforms}`, machine, at), except package lines, lines it cloned, lines whose commands carry a local path or something like a secret (`scrubLocal` or `COMMAND_PATH` would change them) and anything `readLineRecord` would not accept; only the machine that created a record updates it, by compare-and-swap and only when it changed. Then it clones the lines of the other machines whose name is not in the factory file into `ZERO_HOME/lines/<name>` (`FactoryHome.lines`), from `https://github.com/<account>/<name>.git` only, and adds them with `addSharedLine` (through `editConfig`); a line that exists is never changed. The clone goes to a temporary `.<name>-*` folder there, renamed once it is whole and has the base branch; a folder already cloned from that repository by a cut pass is used as it is, and any other folder is refused. `gitCloneLine` (injectable as `DaemonOptions.cloneLine`) is git on its own with a 30-minute limit, https only, no prompts and no credentials of zero's: the person's credential helper gives them. `unattendedWhy` keeps out lines for another platform (the line's optional `platforms`: win32, darwin, linux) or that need an engine no chain here has, checked again on every pass. kv `coord:line:<name>` (`LineState`: `cloned`, `unattended` or `failed`, with `why`) keeps what was done: a `cloned` line taken out of the file by hand does not come back until `zero unirse` runs again (`forgetTakenOut`), and one this machine published itself never does, and a `failed` one is tried again after an hour (`CLONE_RETRY_MS`). The daemon's pass and `zero unirse` may clone a line at the same time: the first clone to finish stays, and a line the other process already added counts as cloned. `linesAway` (the `unattended` and `failed` lines whose name is not in the file) is `FactoryStatus.linesAway`, only with `distributed`, shown by `formatStatus` and the panel summary (`lineAwayLine`). `readLineRecord` is strict (`GITHUB_REPOSITORY`, `LINE_NAME`, `REF_NAME`, commands with no control characters up to 2000 each, no credentials) and gives back only the known fields. The setup and verify commands of a cloned line run on this machine: whoever can write in the coordination repository can add lines, and nothing else of the configuration.
- Where each record lives, under `refs/heads/zero-coord/` of the coordination repository: `machines/`, `claims/`, `queue/`, `sources/`, `progress/` and `probe/` (first two parts), and `lines/`, `spend/`, `status/` and `decisions/` (third part). Each has its `*Ref` and its strict reader in `src/coord/protocol.ts`; a new one needs both, is written only when it changed, and carries no paths, secrets or prompts. A record never changes another machine's configuration, with one exception: `lines/` may add a new line. Orders to another machine's job are only answering it and deciding a proposal; `stop`, `discard`, merging and the trace stay with the machine that has it.
- The person in charge reads about it in both READMEs: 'Several machines' / 'Varias máquinas' and 'Linux machine in the cloud' / 'Máquina Linux en la nube', the last subsections of Getting started, whose pieces `test/docs.test.ts` checks. `test/adr-distribuida.test.ts` checks the ADR. Nothing exercises the Linux guide end to end (rootless Podman, a keyring with no desktop, the systemd user service after a restart, the logins, the tunnel).
