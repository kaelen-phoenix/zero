# Production line

The line's state machine, its stations, verify, the dependency check, the regeneration drill and how a job ends.

- `src/line/`: the production line. `runner.ts` is the state machine (checkpoints, attempts, policy). Each station has a module (`spec`, `verify`, `review`, `integrate`); `security` reuses `review.ts` with its own instructions. Once a spec is valid and feasible, and before anything is written, `specStation` passes it through `uniqueRequirementNames` (`src/line/spec.ts`): a requirement name repeated in the request or in `existingRequirementNames` (the capability's main spec and other unarchived changes' deltas, compared like openspec's fold) gets the suffix ` (<job id>)`, then ` (<job id>-<n>)`, so `openspec archive` does not fail with `already exists` and no extra model call is spent. It only sees the work copy, so two unintegrated jobs can still repeat a name. A spec may carry `stages` (at least 2 and at most `MAX_STAGES`, checked by `specProblems`; `specStages`, `jobStage`): `buildLoop` runs build, the writing agents and verify per stage, records `stagesDone` on the job (resetting attempt and feedback) when a stage passes verify, so a cut or failed later stage is rebuilt alone on the earlier commits, and runs dependencies and the reviewers once after the last; `maxAttempts` counts per stage. A build cut by its time limit (`AgentRun.timedOut`) spends an attempt like any other failure, but its feedback names the limit of `stations.build.timeoutMinutes` and says that the work is still uncommitted in the work copy, to go on from there; while it resolves a merge conflict it names the limit and the conflicted files only, because `startMerge` starts the merge again. `describeJobStatus` and the panel's `LineRow.stage` show `etapa n de N`. A call the engine refused itself (`engineOut` in `runner.ts`: `quota.limited` or `signedOut`, an expired session) goes on with the next engine of the station's chain that is not paused (`goesOn`) without spending a spec try or a build attempt; without one, `quotaStop` puts the job back to `queued` at the same station (a cut build attempt is given back and its `zero.attempt` span ends with the neutral `engine quota or credit used up`), and it resumes once the budget's pause is over.
- Job ends, cleanup and retries (`src/line/policy.ts`, `src/line/finish.ts`): `policy.ts` is the only place that decides when the owner is asked. `finish.ts` is the only way a job ends; a work copy it cannot remove (EBUSY on Windows) never changes the job's end: `finalizeJob` records it as kv `cleanup:<job>` (`src/line/cleanup.ts`), the daemon's `retryCleanups` pass (`cleanupPass`, on the intake interval) tries again and deletes the record once it goes (never while that job is at work again in the same folder, and `takeBack` leaves a pull request in conflict for later while its job has one), and `zero status` shows `Limpiezas pendientes:` meanwhile. A passing network cut that reaches `runJob`'s final catch (`isTransientNetworkError`: ECONNRESET, ETIMEDOUT, EAI_AGAIN, ECONNREFUSED or EPIPE in the `code` or message of the error or its causes) puts the job back in the queue from its checkpoint, at most 2 times in its life (kv `network-retry:<job>`): uncommitted changes are dropped and a cut build does not spend an attempt. A locked folder (`isLockedFolderError`: EBUSY the same way) is handled alike, at most 2 times (kv `busy-retry:<job>`), after killing what was left in the work copy (`RunnerDeps.killLeftovers`); the daemon also kills the leftovers in each interrupted `running` job's copy before re-queuing it (`DaemonOptions.killLeftovers`), and `mergeIntoBase` never fails over its temporary `merge-<job>` folder: a locked earlier one is replaced by a fresh name and one it cannot remove after the merge is recorded as `cleanup:<job>-merge` (`IntegrateOptions.onLeftover`). Anything that fails while first preparing the work copy (`SetupFailed`) is never retried, since a resumed job would skip setup. `retryJob` (`src/app.ts`, `zero reintentar`) puts a failed job with a spec back to `queued` from its checkpoint with `attempt` 0; a failed job without a spec whose reason does not start with `SPEC_REFUSAL` (for example two spec tries cut by a signed-out engine) goes back from the start (`checkpoint` none, `attempt` and `stagesDone` 0, no `station`, `feedback`, `finishedAt`, `worktree`, `base` or `branch`, `stopRequested` false, kv `network-retry:<job>` and `busy-retry:<job>` deleted), while one refused at spec keeps the error that asks to request it again. A 422 `already exists` when opening a pull request ends in `integration-blocked`.
- AI attribution in the job's commits (`scrubBranch` in `src/attribution.ts`): right after `copy.publish()` and before `integrate` (merge, branch, pull request and the update of an existing pull request), the runner rewrites the job's unpublished commits in the line's repository, and `pushProgress` (`src/coord/progress.ts`) does the same before its push. Unpublished means reachable from `refs/heads/<branch>` and not from the `keep` list (the runner passes `line.baseBranch`, `copy.base` and the pull request's previous head `refresh.head`; the progress push passes its lease SHA and `copy.base`) nor from any remote-tracking ref, so base commits, commits already pushed and the head of the pull request keep their SHAs and every later push is a fast-forward. Each commit whose message has lines `stripAttribution` removes (or whose parent was rewritten) is written again with `git hash-object -t commit` from its raw object: same tree, author and committer with their dates and other headers, parents mapped within the range, only the attribution lines gone (a `gpgsig`, no longer valid, is dropped). The same originals always give the same SHAs, so a box copy that publishes its unscrubbed branch again ends at the same tip. The branch moves with `update-ref <new> <old>`, never by force; a branch with no attribution is left untouched.
- `src/line/discard.ts`: `discardJob(ctx, id, {reason, via, api})`, behind `zero descartar <trabajo> [--motivo]`, the chat's `zero_discard` and the panel's `Descartar`. Takes a failed, queued or waiting job, or a delivered one whose pull request is open (asked to GitHub; when it cannot be, its `MergeState` and `delivery.commit` decide), and refuses a running, stopped or otherwise delivered one before writing anything. It drops the `prRefreshKey` mark, ends the job `stopped` through `finalizeJob` (reason `discardedByYou`, `delivery` kept), and only then comments on and closes the open pull request (`MergeApi.close`, optional) and deletes the branch (`delivery.branch`, else `zero/<id>`) locally when it is not checked out and on GitHub: never a line's base branch nor one outside `zero/`. GitHub and git failures go to `DiscardOutcome.problems` and never undo the end; `formatDiscard` tells it all. The job's trace gets a `zero.discard` span. `discardResolved(ctx, now, merges?, onClosed?)` (the daemon's `closeResolved` on the intake interval, GitHub pass `resolved` of the meter, and the start of `unjamPass` and `urgentUnjamPass`) closes on its own, `stopped` through `finalizeJob` with a reason of `discardedByFactory` (`Descartado por la fábrica: …`), the failed jobs of non-package lines whose work is already in: GitHub says the pull request in `delivery.url` was merged, or the branch (`delivery.branch`, else `zero/<id>`) is in the freshly fetched `<remote>/<baseBranch>`, as an ancestor with work of its own (`ownWork`: a `zero(<id>)` commit, or one made on the branch, so a job that failed before its first commit stays failed) or because every path it changed since the merge-base is the same there. It returns how many it closed and calls the optional `onClosed` with the `ResolvedClosure` (`{ line, job }`) of each right after its `finalizeJob` (a throwing callback is only logged). It asks nothing of the person in charge, deletes no branch and leaves every other failed job alone. Kv `resolved:<line>` (`ResolvedLook`) keeps it to one look per line a minute (`RESOLVED_MS`) unless another job failed, skips comparisons whose two tips did not move, and asks about a pull request closed without merging once a day.
- `src/line/verify.ts`: the verify station. `operationArtifacts` holds the shapes of the factory's operation output (added files only, minus the line's `allowedArtifacts` and the Markdown of the job's own specification), including regeneration drill output (everything under a `drills/<id>/` folder holding an added `informe.md` or `resultado.json`, and that pair added in the same folder anywhere, found over all added files, allowed ones included); `verifyChange` runs it before protected paths and commands, failing the attempt, and `runJob` runs it again over the whole change just before integrating, failing the job. Each verify command's time limit comes from `verifyTimeoutMs` in `src/line/pace.ts`: the line's `verifyTimeoutMinutes` (20 when absent) and never less than twice the slowest of its last 5 passing runs on that line in 30 days (read from the `zero.verify.command` spans, `zero.run_ms` when present; history alone gives at most 4 hours); a command over its limit says the limit and the option in its feedback. `slowestPassMs` in the same file gives that slowest run, and `verifyRequest` in `runner.ts` uses it to write each command's known duration (minutes, rounded up) in build's prompt: one over a third of `stations.build.timeoutMinutes` comes with the instruction not to run it whole and to run only the tests of the files touched, since verify still runs every command whole; without history the prompt names the commands alone. It is only an instruction: zero does not keep build from running the suite. A command that fails with output that reads like the machine and not the change (`machineTrouble` in `verify.ts`: a test over its own timeout, no memory, EBUSY, a dead worker, a network cut) is run once more before the attempt fails (`zero.verify.machine` on the failed span, `zero.verify.again` on the second). The same file holds `localCommands`, the queue through which the runner's local `shell` (setup and verify outside the box) lets `commandConcurrency` commands run at once across jobs; waiting does not count against the time limit, and an aborted wait never runs. `prepareWorkCopy` tries a failed first preparation once more in a fresh copy (`SETUP_TRIES`) before `SetupFailed`.
- `src/line/dependencies.ts`: the dependency check, off unless a line sets `checkDependencies`. After verify and before the reviewers, `buildLoop` runs `newNpmDependencies` (changed package.json and package-lock.json read with `git cat-file blob` at HEAD and at the merge base, up to `MAX_MANIFEST_BYTES`, a HEAD manifest that cannot be read or parsed counting as `unreadable` and reaching security as unverified; lock entries resolved outside `https://registry.npmjs.org/` and non-registry specs are left out) and `checkDependencies` (OSV querybatch and deps.dev from zero's process through `RunnerDeps.fetch`, 10 s per request). A `MAL-` advisory, a 404 on deps.dev or an invalid name fails the attempt; recent (under 7 days) or first versions and unverified packages (any request failure, never thrown) reach only the security prompt through `dependencyBlock`.
- `src/line/drill.ts`: the regeneration drill behind `zero simulacro <line> <capability> --archivos <glob>... [--usd N] [--conservar]` (`regenerationDrill` in `app.ts`, which refuses before creating anything: unknown line, `isolation: container`, andon, `budgetState` reached, `--usd` not positive or above `limits.usdPerJob`, no `verify`, no `openspec/specs/<capability>/spec.md` at the base branch, `<ZERO_HOME>/drills` inside a line's or the current folder's repository (`versionedAt`, shared with `saveReport`), no file left by `drillFiles`). `runDrill` clones the base branch with `--no-hardlinks --no-local` into `<ZERO_HOME>/drills/<id>/copy`, removes the matched tracked files (never tests, `isTestFile`, nor `openspec/`), replaces `.git` with a fresh one-commit repository, runs `setup` (`DRILL_SETUP_MS`, 20 minutes each), makes one `build` call (`pickEngine`, `maxBudgetUsd`, `DrillOutput` with `missing`), runs `verify` (each command with the `verifyTimeoutMs` a job gives it, but outside the `localCommands` queue and without adding to its history) and writes `informe.md` and `resultado.json` next to the copy, which it then removes in a `finally` (`DrillDeps.removeCopy`; a failure is only logged) unless `keep` (`--conservar`) asks to keep it; `DrillResult.copyKept` and the report's `Copia de trabajo:` line say which. `DrillCommand.timeoutMs` keeps the limit each command ran with; the report of a cut says its minutes and, for verify, that `verifyTimeoutMinutes` changes them. Outcome: `inválido` when a test or spec differs from the copy's commit, `alcanzan` when every file came back, verify passed and the agent ended ok without its cap, `sin medir` when all that holds except that every verify command that failed was cut by its time limit (a cut setup does not count), else `no alcanzan`. `formatDrill` (`src/format.ts`) is the terminal's text.
