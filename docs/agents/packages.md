# Packages

Agent packages: manifests, stations, tabs, repositories, and packages installed from git.

- `src/packages.ts`: agent packages, a way to extend zero with third-party or own agents. `loadPackages` (never throws) reads `zero-package.yaml` (`ManifestSchema`, `PACKAGE_INTERFACE`) from each entry of `packages` in the factory file (a `path` or an `npm` name under `<ZERO_HOME>/packages/node_modules`) and `factoryConfig` sets the result on `config.loadedPackages`, which never comes from the file. A broken package stays out whole, as a problem in `factoryStatus`, `packageList` and once in the log (`warnOnce`). Its agents join `lineAgents` with origin `package`, after the file's global ones, with the entry's `engine` and `model`; its skills are `<package>:<skill>` in `availableSkills` (`src/skills.ts`), with no links in their folders (refused on load, left out of the staged copy by `stageSkills`). Stations load only with `allowCode: true` and a real folder outside the lines' repositories and `worktrees`/`jobs`. `src/line/packages.ts`: `packagesPass`, the last idle pass of the daemon, runs each station at most once per `everyMinutes`, importing its module and building its `ctx` (`StationContext`, interface 1); `ctx.runAgent` records `package:<package>/<station>`, which `scoutSpent` counts in `limits.usdPerNight`. A station whose manifest declares `requests: { perLinePerDay: N }` may call `ctx.requestJob({ line, text })`, which goes through `requestWork` with source `{kind: 'package', package, station}` and returns `{ id }` or, never throwing, `{ reason }` (pass ended, no `requests`, unknown line, andon, budget, quota in kv `package:<package>/<station>:requests:<line>` per local day, counted only once the job exists). An optional `maxUsd` becomes the job's `budgetUsd` (`requestWork`'s `budgetUsd`, refused when not finite, not positive or above `limits.usdPerJob`, before any quota is spent); `ctx.job(id)` gives a `PackageJobView` (status, cost, budget, waiting, cleaned reason, delivery mode and commit) only for jobs whose source is that same package. The text is cleaned with `publicText` plus the station's secret values and cut to 4000 characters. `requestBlock` in the runner presents it to agents as a third party's data; it does the same, from `job.source` alone, for `night-shift` (drafted by scout, possibly with web material, even if approved) and `research` (built from a web note) jobs, so only owner requests say `The owner sent`. These jobs follow their line's level and integration without `nightShiftHold`; the daemon treats them as low priority (`lowPriority`, shared with the night shift's own jobs: after the others in `ownerFirst`, one at a time and only with nothing else queued or running). `scheduledPass` (same file; the daemon's `runSchedules`, a background pass on the intake interval, whatever the line is doing and not held up by the budget) runs the module's `scheduled(ctx, { at })` for each local time of a station's manifest `schedule`, at most once per local day (kv `package:<package>/<station>:schedule:<HH:MM>`, the day, marked before the call) and only within 2 hours of that time (`dueSlots`, oldest first, yesterday's included); the andon or a missing secret leaves the time unmarked. There `ctx.runAgent` throws synchronously, so it never reaches a model; the rest of `ctx` is the same as in `pass`. A station whose manifest declares `onDemand: true` can be asked for one extra `pass` (`requestStationRun` in `app.ts`, behind `zero package run <package>/<station>` and `zero_package_run`): it refuses with a reason (format, unknown or not loaded, no `onDemand`, already pending, andon, budget), otherwise records kv `stationOnDemandKey` (the request time). `onDemandPass` (same file; the daemon's `runOnDemand`, a background pass on the intake interval under the packages switch, like `runSchedules` outside `idlePasses`, awaited on exit and cut on shutdown) calls `pass(ctx, { onDemand: true })` whatever the queue, held back only by the andon, the budget and missing secrets, without touching `stationLastKey`, and clears the key right before the call (or when the module cannot run); `packagesPass` runs only regular turns and skips a station with a pending request. A station whose manifest declares `whenBusy: true` (`PackageStation.whenBusy`, default false; a non-boolean leaves the package out) has its regular turn in `busyPass` instead (same file; the daemon's `runBusyStations`, a background pass on the intake interval under the packages switch, like `runOnDemand`, before the self-update switch and the job start, so it runs with jobs queued or running, with a ready self-update waiting and while the box is waited for; awaited on exit and cut on shutdown): `runStation` with the shared `stationLastKey`, held back by the andon, the budget, missing secrets and `busyStations`, skipping a pending on-demand request, and never looking at the job list; `packagesPass` still runs them when idle, sharing `stationLastKey` and `busyStations`, so it is one turn per period across both. `packageList`'s station view carries `whenBusy: true` (` · corre aunque la fábrica esté ocupada` in `zero package list`) and `FactoryStatus.whenBusy` lists them as `<package>/<station>` (an `Estaciones que corren aunque la fábrica esté ocupada:` line in `formatStatus`); the panel shows the same mark next to the state in the station's card on `/packages` (`packageStation`) and the same line in the summary (`overviewPage`), with the names escaped. `runTurn` keeps one turn per station at a time in the process (`busyStations`); a busy station's turn returns without marking anything. The request may carry the owner's text (`--pedido`, the chat's `request`, the panel's `pedido`): `requestStationRun` cleans it with `stationText` (the station's secret values, `publicText`, 4000 characters) into kv `stationOnDemandRequestKey`, and the pass gets `{ onDemand: true, request }` (exactly `{ onDemand: true }` without one); only `requestStationRun` writes it, never a station's `ctx` or another intake. An onDemand station may also declare `uploads` (`{ maxMb, extensions }`, at most `MAX_UPLOAD_MB`, default 20 and `['.zip']`; refused without `onDemand`): `uploadToStation` in `app.ts` (behind `zero package upload <paquete>/<estación> <archivo>`, the chat's `zero_package_upload` (an absolute `path` read lazily from disk, or strict base64 `content` with `name`; the remote server refuses `path`; not in `READ_TOOLS`) and the panel's multipart POST `/packages/upload`, which reads the body through `limitedBody` up to the station's limit before and instead of `readForm`) checks everything `requestStationRun` checks before writing, streams the file to `<package-data>/<package>/uploads/<station>/<time>-<uploadName>` (removed past `maxMb`, without the zip signature or on any refusal) and asks the run with kv `stationUploadKey`, which only that turn reads (and clears) as `ctx.upload` (`StationUpload`). `ctx.limits` is a frozen copy of `limits.usdPerJob`; `requestJob` checks the factory's own. `ctx.unzip(zip, dest)` wraps `src/unzip.ts` (pure, no dependency: stored and deflated entries only; the whole archive is checked before writing and refused on encryption, zip64, link entries, absolute, drive or `..` names, `:`, links on the way to the destination, more than `MAX_ENTRIES` or more than `MAX_UNZIPPED_BYTES` declared or real), with the zip inside the data folder and the destination there or in one of the package's repositories (never their `.git`, `noGit`). A station whose manifest declares `repositories: { perDay }` gets `ctx.repos` (`StationRepos`, never throwing, refusing another package's repositories): `create(name, { from, setup, verify })` (`REPO_NAME`; at most `perDay` a local day, kv `package:<package>/<station>:repos:<day>`, counted once the line exists) makes `<ZERO_HOME>/package-repos/<package>/<name>` (`packageReposDir`) with one commit on `main`, seeded through `unzip` when `from` names a zip of the data folder, and adds the line `<package>-<name>` (`packageLineName`) with `integrate: merge`, `package: <package>` (`LineConfig.package`) and those commands through `addPackageLine` in `app.ts` (`editConfig`); `archive(name, file)` runs `git archive --format=zip` of `main` to a `.zip` path of the data folder; `remove(name)` refuses while the line has a queued, running or waiting job, then `removePackageLine` and the folder. `ctx.requestJob({ repo, text, maxUsd })` opens a job on that line, which delivers by `mergeIntoBase` with no remote; `ctx.lines` and `requestJob` see only the owner's lines and the station's own package's (`visibleLines`), and scout, unjam and research skip lines with `package`. Each on-demand turn records two kv entries through `StationTurn.ended`: `stationOnDemandLastKey` (`OnDemandRecord`: `asked`, `startedAt`, `endedAt`, `outcome` `ok`/`failed`/`timeout`/`stopped`/`not-run`) and `stationRunKey` (`StationRunRecord`: `requestedAt`, `request`, `startedAt`, `running`, then `ended` with `done`, `failed`, `timeout` or `stopped`, `finishedAt` and a cleaned `error` of at most 600 characters); `waitStationStart` (CLI 2 minutes, chat 30 s) waits for the `stationRunKey` record of that `requestedAt` to start. A pending request shows, read-only, as `onDemandPendingSince`/`onDemandRequest` on `packageList`'s station view (with `lastOnDemand`, the record; `corrida a demanda pendiente desde HH:MM` in `zero package list`) and in `FactoryStatus.onDemand` (a `Corridas a demanda pendientes:` line in `formatStatus`, with `request` only when present); `FactoryStatus.onDemandRuns` (`onDemandRuns` in `app.ts`, the last 24 hours or still running, `stale` past `timeoutMinutes` with no end) is the `Corridas a demanda recientes:` line (`describeOnDemandRun`/`onDemandState` in `src/format.ts`) and `FactoryStatus.stationRuns` the `Corrida a demanda de <station>:` lines (`describeStationRun`); the panel summary shows pending and recent runs, the briefing a `## Corridas a demanda` section, and the panel's `/packages` page (`packagesPage`, "Paquetes" in `NAV`) the stations, with a "Pedir ahora" form on onDemand stations that posts to `/packages/run`. `jobOrigin` in `src/format.ts` is their label in status, panel and line view; the briefing has its own section and the monthly report's `originLabel` a case. A manifest's `tabs` (`{name, title, data, categories?}`, no `allowCode` needed) become `LoadedPackage.tabs`: read-only panel tabs at `/packages/<package>/<tab>` (`packageTabs`/`packageTabView` in `app.ts`), listed in every menu through `TABS_MARK`, which `send` in `src/panel/server.ts` fills. `src/package-tabs.ts` (`readTabData`, `TabDataSchema`, `safeUrl`) reads the JSON from the package's data folder `<ZERO_HOME>/package-data/<package>` (`FactoryHome.packageData`, `packageDataDir`, the stations' `ctx.dataDir`, created before each pass) without following links out of it, up to 1 MiB and 500 items; no package code runs in the panel, every text goes through `esc` and only http(s) urls become links. An item's optional `file` (relative, no `..` or drive, `pathProblem`) becomes a `Descargar` link only when `dataFile` finds it a regular file inside the data folder; GET `/packages/<package>/<tab>/files/<path>` (session required) serves it as an `application/octet-stream` attachment (`downloadName`) through `packageTabFile`/`tabFile`, only when the tab's current data lists exactly that file and it is at most `MAX_DOWNLOAD_BYTES`, else 404. `loginPage` returns to the link's own path after exchanging the key. `packageList`/`packageAdd`/`packageUpdate`/`packageRemove` in `app.ts` back `zero package`; every factory-file edit in `app.ts` goes through `editConfig`, which keeps `loadedPackages`.
- Packages from git: `src/package-source.ts` (pure, imported by `config.ts`) has `isGitSource`, checked before `looksLikePath`, and `parseGitSource`, which refuses credentials, protocols other than https and ssh and anything git could read as an option, in errors that never repeat the source. `src/package-install.ts`: `GitRunner` (the real one has no shell, stdin closed, `GIT_TERMINAL_PROMPT=0`, `GIT_ALLOW_PROTOCOL=https:ssh`), `findOnPath` and `runNpm`: git and npm start by absolute path, from absolute PATH entries only, with no shell and from a folder outside the package (`git -C`, `npm --prefix`, npm through `process.execPath` and `npm-cli.js`), since on Windows a bare name or cmd.exe would find a `git.exe` or `npm.cmd` planted in the package's folder; `npmCiArgs`, `lockProblem` (npm builds a git dependency by running its code, `--ignore-scripts` or not, so `package-lock.json` and `npm-shrinkwrap.json` may hold only https registry tarballs and local links: read by `folderLockProblem` when adding, on folder updates and in `realDependencies`, by `lockProblemAt` from the new commit while planning a git update, before confirmation and shutdown; `npmSpecProblem` judges a package from npm through a lock built in a throwaway folder, and `runNpm` sets `npm_config_allow_git=none`; since `npm ci` empties `node_modules` of the package and each workspace through links, the same two functions refuse, when there is a lock, a `node_modules` that is not a real folder, a link leaving the package, `workspaces` patterns that could leave it and lock paths outside it), `manifestAt`, `widening`, `cleanText` for third parties' text shown on a terminal, and the kv records: `package-update:<name>` (`{seen, at, error?}`) and `package-lock:<folder>` (the lock's hash). A git entry in the factory file is `{git, path, commit}`. `packageAdd` clones into a temporary folder inside `<ZERO_HOME>/packages/git`, checks manifest and fit there, shows the summary, asks through `confirm` (default no), renames to `packages/git/<name>`, runs `npm ci --omit=dev --ignore-scripts` if there is a lock and only then writes the entry. `packageUpdate` first only looks (guards in `gitFolderProblem`, fetch, commits, widening and confirmation; a commit whose manifest is not a regular file, `manifestNotAFile`, which `packageAdd` refuses too, or cannot be read through `manifestAt` stops there), then with something to apply calls `shutdown` once, runs each package's `ApplyUpdate` (git returns to the previous commit on any failure, including a manifest on disk that differs from the one judged) and `start` once, only when the status was `stopped`. `src/line/package-updates.ts`: `packageUpdatesPass`, a daemon pass that at most every 24 hours (kv `package-updates:last`) records `ls-remote` and `npm view` results without touching a package's folder (it asks `ls-remote` for `<ref>` and `<ref>^{}`, since git lists an annotated tag's peeled line only when asked by pattern; with no reference, for `HEAD`); `packageList` reads only what is on record.
- Guests: a manifest's optional `guests` (`ManifestGuestsSchema`, strict: `scope: { name, title }`, `tabs`, `run`, `upload`) says what the panel's guests may be offered; `packageGuests` leaves the package out when a name does not exist, repeats or does not accept that action (`run` needs `onDemand`, `upload` needs `uploads`) or nothing is offered, and `LoadedPackage.guests` is set only when declared. A tab's item may carry `scope`: `packageTabView`, `packageTabFile` and `tabFile` take an optional list of values, and with it only items whose `scope` is exactly one of them exist (items without it are hidden, categories and files come only from the visible ones). zero enforces it, never the package. A guest's run or upload is asked through `requestStationRun`/`uploadToStation` with a `StationAsker`, kept in kv `stationOnDemandGuestKey` next to the request and cleared with it, and reaches the station as `pass(ctx, { onDemand: true, request?, guest: { name, scope? } })`; the owner's call carries no `guest`. `StationRunRecord.guest` (id and name) shows the owner who asked, in `/packages`, `zero package list` and the status. See [Panel](panel.md).
