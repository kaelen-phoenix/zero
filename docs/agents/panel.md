# Panel

The control panel, the remote chat and its tunnel.

- Remote chat (`docs/adr/0009-chat-remoto.md`, written as `docs/adr/0007-chat-remoto.md` until the distributed factory took 0007): MCP over streamable HTTP for a chat on the phone, served by the panel's server through its tunnel and off unless kv `mcp.remote` is `on` (`setRemoteMcp` in `app.ts`, behind `zero mcp remote on|off` only; no chat tool touches it). `src/mcp/oauth.ts` is zero's own OAuth 2.1 authorization server over kv (`oauth-client:`, `oauth-code:`, `oauth-grant:`, `oauth-access:`, `oauth-refresh:`, only SHA-256 hashes of codes and tokens): dynamic registration with https or loopback redirects, single-use 5-minute codes bound to client, exact redirect and an S256 challenge, 1-hour access and 7-day rotating refresh tokens, scopes `zero:read`/`zero:act`, a reused code revoking its grant, revocation per client; the clock is injected. `src/mcp/http.ts` (`createRemoteMcp`, dispatched in `src/panel/server.ts` before the cookie check, `isRemoteMcpPath`) serves the RFC 8414 and RFC 9728 metadata with `panel.remoteUrl` as issuer and resource (503 without it), `/oauth/register|authorize|token|revoke` and a stateless `/mcp` that needs a Bearer token and a Host of the tunnel or 127.0.0.1. `/oauth/authorize` needs the panel's session (the login returns to the path with its query through `safeBack`) and issues a code only on a same-origin POST with `confirm=1` (`authorizePage`). `/mcp` builds `createZeroMcpServer` with `remote: { scope, client }`: a read-only token gets only `READ_TOOLS`, and zero_merge, zero_stop, zero_proposal_decide, zero_egress_block and zero_answer approving a `protected-path` question are held as kv `mcp-pending:<id>` (`holdRemoteAction`, 15 minutes, `PENDING_TTL_MS`) and run once through `confirmRemoteAction`. `remoteChatView` backs the panel's `/remote-chat` tab ("Chat remoto": clients, revoke behind `confirm=1`, held actions with Confirmar) and `zero mcp clients` (`formatRemoteChat`); `zero mcp revoke <cliente>`, `zero mcp pendientes` (`formatPendingActions`) and `zero mcp confirmar <id>` do the rest. The stdio server is unchanged.
- Fixed address for the remote chat (`docs/adr/0008-tunel-con-nombre.md`): `panel.tunnel` in the factory file (strict, only `hostname`, a lowercase DNS name never under `trycloudflare.com`) plus the secret `CLOUDFLARE_TUNNEL_TOKEN` make `tunnelKeeper` (`src/panel/tunnel.ts`) run a Cloudflare named tunnel (`tunnel --no-autoupdate run`, the token only as `TUNNEL_TOKEN` in the child's environment) and set `panel.remoteUrl` to `https://<hostname>` once cloudflared prints `Registered tunnel connection`; without either it keeps the quick tunnel (a hostname without token is a logged-once `problem`). Reopening uses the quick tunnel's growing waits. kv `panel.tunnelState` (`TunnelState`: `mode`, `connectedSince`, `failures`, `lastExitAt`, `problem`) becomes `FactoryStatus.tunnel` (with `hostname`) while `panel.remote` is on, shown by `tunnelLine` in `src/format.ts` as `Túnel:`; `RemoteChatView.stable` says the open address is the configured one, for `zero mcp remote on`, `formatRemoteChat` and `/remote-chat`.
- `src/panel/`: the control panel the daemon serves on 127.0.0.1. `server.ts` (session from the key in the link's fragment, Origin checks, actions through `app.ts`), `html.ts` (server-rendered pages in one `page()` layout: a CSS-only collapsible side menu (`NAV`, inline SVG icons, `#nav-toggle` checkbox, a dropdown on phones), the site's palette, fonts and logo in one inline `STYLE` with light and dark tokens, and shared status tokens behind `class="chip" data-status`; the production line view at `/line` is a board of eight lanes (the seven stations plus `out`) with compact job cards, which refreshes its cards from a fragment pushed on the `/line/events` stream, polling as a fallback, the job page's `Fundir` button for a delivered GitHub pull request not yet merged or closed (`/job/<id>/merge`, a confirmation page until `confirm=1`, then `mergePullRequest` with via `panel` and `PanelOptions.merges`, the daemon's metered real adapter), the read-only `/about` and `/agents` pages built from `factoryGuide` in `app.ts`, the `/proposals` tab built from `proposalsView` in `app.ts`, whose approve button only shows a confirmation page until the form carries `confirm=1`, the `/requests` tab ("Pedidos") built from `requestsView` in `app.ts` (typed form through `requestWork`'s `type`/`title`/`description`, `REQUEST_TYPES`; list with line and estado filters; answer, and stop behind a `confirm=1` page), and the `/research` tab built from `researchView`, whose "Pedir trabajo" button confirms the same way before `requestFromResearchNote`; the read-only `/monitor` tab built from `monitorView` in `app.ts`, filtered by `periodo` through `parsePeriod`, aggregates jobs, spans (`store.spansSinceAny`; tokens are `gen_ai.usage.*`, which the Claude engine reports through `EngineResult.tokens`), `budgetState` windows and `mergeKey` states without writing or asking GitHub; the read-only `/control-room` tab ("Sala de control", `src/panel/control-room.ts`, its own dark console in `CONTROL_STYLE`) built from `controlRoomView` in `app.ts`: topbar, event ticker, station graph with a decisions column, 24-hour series per line, agent bus, trace, engines and alerts, refreshed by `CONTROL_REFRESH` from `/control-room/events`, whose dots move in place by `data-job`; every live stream is a `StreamFeed` (its render, and what of it counts as a change: the room's clock does not) on the one shared watcher), `charts.ts` (the monitor's gauges, bars and line chart as inline SVG), `key.ts` (key in the keychain), `tunnel.ts` (optional cloudflared quick tunnel, downloaded with consent and kept by the daemon).
