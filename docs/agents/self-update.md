# Self-update

How far the installed copy is from what was merged, and the factory updating itself.

- `src/install-freshness.ts`: how far the installed copy of zero (`installRoot`, the folder holding the running dist/cli.js) is from what was merged. `checkInstall`, a daemon pass on the intake interval (`DaemonOptions.install` injects the folder and the `GitRunner`; off in `once` runs without it), asks git at most once an hour and stores kv `install:freshness` (`InstallFreshness`: `checkedAt`, `behind` against the upstream or `<remote>/<branch>` after a best-effort fetch, `staleBuild` when a file under `src/` is newer than `dist/cli.js`, `repository` when the remote is on GitHub, or only a `problem` for a folder that is not the root of a git repository). While `installBehind`, `factoryStatus` sets `FactoryStatus.install` and `installLine` in `src/format.ts` gives the `Instalación atrasada` line of `formatStatus` and the panel summary; the briefing gets an `## Instalación` section.
- `src/self-update.ts` and `src/self-update-switch.ts`: the factory updating itself, off unless the factory file says `selfUpdate: { enabled: true }` (strict: `remote`, `branch`, `startTimeoutSeconds`; no chat tool touches it). `selfUpdateCheck` (the daemon's `checkSelfUpdate` background pass, off in `once` runs unless `DaemonOptions.selfUpdate` is injected) runs once a day or after a job of a line whose repo is the install folder (`installFolder`, the parent of `dist/cli.js`) gets MergeState `merged`; it needs the folder to be its repository's root, on the branch and without tracked changes, fetches and plans only a fast-forward (each distinct problem logged once), then prepares the tip in `<ZERO_HOME>/self-update/<sha>` (`lockProblemAt`, `npm ci --ignore-scripts`, build, `dist/cli.js --version` and the hidden `self-update check`). A failed commit goes to `failed` and is never prepared again, unless the failure came from the machine (`isMachineFailure`: EPERM, EBUSY, EACCES or ENOTEMPTY in the error, a result marked `machine`, a switch that left no result): then `afterFailure` records `retry` (`{commit, at, tries}`, 1 hour doubling up to 24, `RETRY_FIRST_MS`/`RETRY_MAX_MS`) and the check is due again at `at`. The check is also due when the install's HEAD differs from the state's `head`; a tip equal to HEAD (installed by hand) saves exactly `{status: 'idle', checkedAt, head}`, and a `ready` whose `to` is HEAD goes back to that and removes its folder. kv `self-update:state` (`idle`/`ready`/`switching`) and `self-update:history` (last 20, `updated`/`rolled-back`/`failed`). While `ready` the daemon starts no job; with none running and no switch lock held it calls `launchSwitch` (copies the built switch to `switch.mjs`, writes `plan.json`, spawns it detached) and shuts down. The switch lock (`<ZERO_HOME>/self-update/switch.lock`, `acquireSwitchLock`/`switchLockHeldAt`, an exclusive SQLite transaction like the daemon's) is held by `runSwitch` from its start until its result is written: while it is held `importSwitchResult` declares no switch stale, `selfUpdateCheck` prepares nothing and the daemon launches no switch; a switch that cannot take it touches nothing and writes no result. `importSwitchResult` applies only a result whose `to` is the `switching` state's, removes only that result's own prepared folder, and a late `updated` takes its commit out of `failed` and `retry`. `runSwitch` (Node built-ins only) waits for the lock to go, stages the prepared `dist` and `node_modules` in `<install>/.zero-switch/new` (`stagingPath`, git-ignored; a rename or, across volumes, a copy; fresh suffixed names such as `new-1` when an earlier switch left folders there) and compares their file lists (`SwitchFs.list`) before touching the install, swaps the parts only by renames inside the install folder (old ones to `.zero-switch/old`, retried with a growing wait on EBUSY/EPERM/EACCES/ENOTEMPTY, then given up with the part, the code and a hint about another process such as the chat's MCP server), runs `node dist/cli.js --version` from the install folder (`SwitchDeps.check`), `merge --ff-only`, starts `cli.js start` detached and waits `startTimeoutSeconds` for the lock; only then do the old parts go to `self-update/previous`. Any failure renames the new parts aside and the old ones back (never deleting the install's own), `reset --keep <from>` when merged and starts the previous version. A `failed` result caused by the machine (a missing or incomplete part, a locked rename whose code `renameRetrying` keeps, a factory that did not stop in time, the switch lock) carries `machine: true`; a failed `--version`, merge or start does not. It never throws and always writes `result.json` (retried; the entry point also writes one on an uncaught error), then releases the switch lock and only then removes, as best effort, the named folders under `.zero-switch` (its own and the leftovers listed under the lock, never the root as a whole, which goes only when empty, and never an `old` folder still holding a part a rollback could not put back), since a locked file can make that take hours. It writes `result.json`, which `importSwitchResult` moves into the history at daemon start. `selfUpdateStatus` in `app.ts` feeds `FactoryStatus.selfUpdate` (with the state's `retry` when a machine retry is pending), shown as `Autoactualización:` lines (`selfUpdateLines` in `src/format.ts`, a pending retry as a non-alarming `vuelve a intentar pasar a <commit> a las HH:MM (intento N)` through `selfUpdateRetryText`) in status and the panel's summary, and the briefing lists rollbacks, failures and the pending retry. `zero --version` prints `versionText`.
