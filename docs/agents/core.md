# Core

Commands and shared operations, the factory file, ZERO_HOME, state, telemetry, process spawning and the repository's documentation.

- `src/cli.ts`: commands. `src/app.ts`: operations shared by the CLI, the MCP server and the daemon (request, status, answer, stop, briefing, trace). Never duplicate logic between interfaces; add it here.
- `src/config.ts`: `zero.factory.yaml` schema, effective level, `commitAuthor` (global and per line: `zero` or `owner`; with `owner`, `authorEnv` in `src/workspace.ts` passes the line repo's git config identity as GIT_AUTHOR_* to work-copy commits and merge-mode integration, zero stays the committer and is the author when no identity is configured). `src/signature.ts`: zero in the loop's signature (`signature` in the file, global or per line, resolved by `lineSignature`): `withTrailer` on every factory commit (spec, attempts, integration merge), `signText` on pull request bodies (`deliveryBody`), and `signedIssues`/`signedMerges`, with which the daemon wraps its real GitHub adapters per line (each pass hands its api factory the line), so issues and comments end with the text before FACTORY_MARK. `src/attribution.ts` is the single, extensible list of AI-tool attribution (`AI_TOOLS`, `ATTRIBUTION_PATTERNS`: co-author trailers naming an AI tool or its address, `*-Session:` trailers, "Generated with/by ..." lines, bare session links); `stripAttribution` removes those lines and keeps every other one, a person's `Co-Authored-By` and the signature included. `withTrailer`, `signText`, `signedIssues` and `signedMerges` apply it always, with or without a signature (the signed adapters always wrap), `signedIssues` also to created issue titles, and `src/line/integrate.ts` applies it to the pull request title and body and to the title in the merge commit message. `src/init.ts`: `zero init`, `zero line add`. `src/home.ts`: `ZERO_HOME` layout (`drills` holds the regeneration drills, `packageData` the packages' data folders and `packageRepos` their local git repositories). `src/autostart.ts`: `syncAutostart` makes the user-level login entry for this ZERO_HOME (a `zero-<hash>.cmd` in the Windows Startup folder, a LaunchAgent, a systemd user unit) exist exactly when `autostart` (top level of the factory file, default false, never changed by a chat tool) is on; nothing in a container. `setAutostart` in `app.ts` backs `zero autostart on|off`, and the daemon syncs it at start and when a reload changes it.
- `src/setup.ts`: `zero setup` (`runSetup`, every terminal and machine access injected through `SetupDeps`): modes, engines (its `ENGINES` table holds each CLI's login and credentials), limits, isolation, panel, GitHub and, outside a container, the start at login (`autostart`, registered through `SetupDeps.syncAutostart`); it refuses without a terminal, installs nothing and writes through `initFactory` and `editFactory`, so it can run again.
- `src/state/store.ts`: SQLite state (jobs, spans, kv). `listJobs` returns jobs oldest first and at most 1000 unless `limit` says otherwise, so readers of live or recent jobs (`watchedJobs`, the merge-request lookup, self-update, briefing, scout, unjam) pass `limit: -1`. `src/telemetry/`: tracer and the single definition of every metric; `otlp.ts` is the optional OTLP/HTTP JSON export (`telemetry.otlp` in the factory file, header values as secret names resolved through `SecretStore`), a daemon pass that sends finished jobs after a kv cursor (`otlp:cursor`), scrubs with `scrubLocal` and retries a batch at most 5 times.
- `src/shell.ts`: `resolveBin`, `spawnTarget` and `spawnGit` are the only way to start git and engines with a cwd in content zero does not trust: on Windows a spawn without a shell looks in its cwd before PATH (unless `NoDefaultCurrentDirectoryInExePath` is set in zero's own environment, which `test/windows-exec.test.ts` clears), so a bare name goes by the absolute path found in PATH's absolute entries, and one that is not found starts from `TRUSTED_CWD` and fails as any missing program. `sh` is out of scope: verify's commands already run the repository's code and go to the box. `src/leftovers.ts`: what outlives the command that started it. `killTree` (taskkill `/T /F` on Windows, the process group elsewhere, where `sh`, `runProcess` in `src/engines/cli.ts` and the ACP engine start their child `detached`) is how a time limit, a stop or a shutdown ends a command or a CLI engine, since killing only the shell leaves npm, test runners and dev servers running; `killLeftovers(folder)` kills the processes whose command line, executable or working directory is inside a folder (never this process or its ancestors, never a folder less than 3 levels deep), and `removeWorkCopy` in `src/workspace.ts` calls it only when a work copy cannot be removed, then tries again. `src/log.ts`: a log line that cannot be written is dropped and counted (`lostLogLines`), never thrown, and `guardLogStreams` (called by `runDaemon`) keeps an 'error' event of stdout or stderr from ending the daemon.
- `openspec/`: specs (`specs/`) and changes (`changes/`). `docs/adr/`: decisions.
