# Engines and agents

The budget, the engine-agnostic agent runner and its adapters, custom agents, the agent catalog, the recruiter and skills.

- `src/budget.ts`: the single answer to "can the factory start more work?". Subscription plans are limited by their usage windows, read from each agent call's span (`quotaAttrs` in `src/agent.ts`) and, with `distributed`, from the newest reading of the other machines (see [Distributed factory](distributed.md)); per-use billing by the dollar caps, each engine on its own, and for 15 minutes (`UNKNOWN_RESET_MS`) after a call refused because the API key ran out of credit (`Credit balance is too low`, marked `limited` by `claudeResult` and `claudeThrown` in `src/engines/claude.ts`). A subscription the SDK refuses with only a text (`You've hit your session limit · resets 5am`, with no rejected rate-limit event when the plan was used up outside the factory) is marked `limited` the same way, by `refusedQuota`, read only from failed calls: the job waits in the queue (`quotaStop`) and the engine pauses for `UNKNOWN_RESET_MS` at a time instead of failing the work. `pickEngine` chooses each call's engine from the station's chain (`stationChain` in `src/config.ts`: its engine, then the owner's `fallback` list); the factory pauses only when a line station has every engine of its chain paused. Engines report plan usage as `EngineResult.quota`. With `distributed`, the dollar caps (day, night and job) also count what the other machines published (`src/coord/spend.ts`). An expired engine session is not quota: `EngineResult.signedOut` is set by the Claude adapter only on failed calls (`claudeThrown`, a non-success result's errors, an `is_error` result) whose text says `Failed to authenticate`, `OAuth session expired` or `OAuth token has expired` (`signedOutText`; the vendor's text stays in `src/engines/`), never on an answer. The runner carries it to `AgentRun.signedOut` and the span attribute `zero.engine.signed_out` (also written by `fakeAgents` in `test/helpers.ts`), and `engineBudget` pauses an engine whose latest agent call on this machine carries it until `UNKNOWN_RESET_MS` after that call ended, with the reason `falta iniciar sesión en el motor <engine>`; a later call without the mark ends the pause. Zero creates or stores no credentials: the person in charge signs in again.
- `src/agent.ts` + `src/engines/`: engine-agnostic agent runner and one adapter per engine. `EngineResult.model` is the model that answered when the engine reports it (Claude: the key of `modelUsage` with the highest cost); the runner records it as `gen_ai.response.model` and logs when it differs from the requested one. `EngineResult.timedOut`, carried to `AgentRun.timedOut`, is set only when the engine stopped the call at its `timeoutMs`, never on a cancel or another failure: Claude tells its timer from `req.signal` (one `AbortController` serves both; a cancel wins), the CLI engines set it in `outcome` (`cli.ts`) and ACP from `TimeLimitError`. A CLI engine (`src/engines/cli.ts`) that exits 0 without text counts as a failure (`<engine> devolvió salida vacía` plus the end of stderr); codex is judged by its last message, not by stdout. `codex exec` runs with `--json`, so its stdout is JSONL: without the last-message file the answer is the last `agent_message` event, a failed exit tells stderr or else the last `error`/`turn.failed` message, and `codexQuota` reports the plan (a key in `CODEX_API_KEY` or `OPENAI_API_KEY` is `api`; otherwise `codex login status`, run from the engine's temporary folder after the call with a 10-second limit and whose failures change nothing, tells; the last valid `rate_limits` become the windows and imply `subscription` when the session says nothing; a failed call with a window used up is `limited`; a failed call whose stderr or last `error`/`turn.failed` message says `insufficient_quota` or `You exceeded your current quota`, outside a known subscription, is `api` and `limited`, through `codexOutOfCredit`, so the budget pauses codex for `UNKNOWN_RESET_MS`). `codex exec --output-schema` only takes OpenAI's strict mode, so `codexEngine` alone (`src/engines/codex-schema.ts`, pure) sends `toStrictSchema(req.schema)` (closed objects, every property required, optionals nullable through `anyOf` with null, an allowlist of keywords, nothing next to a `$ref`), answers `ok: false` without starting codex, naming the path, when a schema has no strict form (root not an object, dictionaries, free values, tuples, `allOf`), and sets `output` to the answer after `withoutOptionalNulls`, guided by the original schema; `text` keeps the raw message and other engines get the original schema. `opencodeEngine` (built-in `opencode`, in `cli.ts`) runs `opencode run --format json`: the answer is the `text` events after the last `step_start`, `costUsd` the sum of `step_finish` costs, `model` `<providerID>/<modelID>`, no quota, and its permissions (`opencodePermissions`: edit, bash and webfetch denied off `write`, webfetch always) go in `OPENCODE_CONFIG_CONTENT` through `Invocation.env`. `src/engines/acp.ts`: an `engines` entry with `protocol: acp` (no `{prompt}`, refused by `CustomEngineSchema`) becomes `acpEngine`, a minimal Agent Client Protocol client over stdio (initialize, session/new, session/prompt; the answer is the session's `agent_message_chunk` text, `model` the session's `models.currentModelId`, `costUsd` the last USD `usage_update`, no quota); `permissionOutcome` answers `session/request_permission` by access (off `write`, only `read`/`search`/`think` tool calls are allowed), other agent requests get -32601, and the agent is always killed at the end. Both are `unsandboxed`, so zero guards their read-only calls; opencode cannot run in the box (`src/box/credentials.ts`). Above 30,000 characters of `fullPrompt`, `antigravityInvocation` and `opencodeInvocation` send the prompt on stdin and leave a short instruction in `-p`, since the Windows command line stops at about 32K; custom engines keep their own way of receiving it. In `claudeOptions` (`src/engines/claude.ts`), `allowedTools` only auto-approves; on `read` and `web` access `disallowedTools` removes `Agent`, `Workflow`, `WebFetch`, `RemoteTrigger`, `CronCreate`, `ScheduleWakeup`, `SendMessage` and `PushNotification`, and `write` denies nothing. Its `settings` also turn off Claude Code's own commit and pull request attribution (`attribution: { commit: "", pr: "", sessionUrl: false }`), next to `disableAllHooks` and `autoMemoryEnabled: false`; other engines have no such setting, and whatever attribution any engine still writes is removed by `stripAttribution` (`src/attribution.ts`, see [Core](core.md)). The engine and model of each step stay in the report, the trace and the panel. Tests use fake agents, so the final check is the tools in the `init` message of a real run. `agents/*.md` holds the per-station instructions, shared by every engine. `codex: { sandbox: off }` in the factory file (the owner's alone: no chat tool touches it) makes `resolveEngine` return `unsandboxedCodexEngine` (`--sandbox danger-full-access`, `-c approval_policy="never"`, `Engine.unsandboxed`), unless a custom engine is named codex; `BoxAgentRequest` does not carry the option, so inside the box Codex keeps its usual flags. `runHere` in `src/agent.ts` passes that engine's non-`write` calls through `runGuarded` (`src/readonly-guard.ts`): a snapshot in a temporary git repository of its own (no filters, nothing written in the folder or a containing repository; a folder is treated as a repository only if it is its root), plus raw HEAD, `config` and `hooks`, the real index and the references except `refs/remotes`. After the call it puts back only what differs, never `reset --hard` or `clean`, and fails the call keeping cost and quota; the temporary folder stays, named in the log, so what was discarded can be recovered. Anything else changing the folder or its checked-out branch during the call looks like the call's doing. Refs are the whole repository's, so `refChanges` only holds the call to its checkout's branch and, outside a linked worktree, the rest except `refs/heads/zero/*`, branches checked out elsewhere and new tags; those are logged, not rewound. Tracked files under an ignore rule are compared too (`trackedIgnored`). The daemon starts no job in a repository under a guarded call (`beingGuarded`) and a guarded pass call waits for the jobs running in its folder (`passExecute`). In `src/daemon.ts`, `passRunner` (issue replies, scout, research, the packages' stations) (through `passExecute`) sends unsandboxed engines to `BoxExecutor.execute` when the box is ready at that call, the rest to `runHere`; a job keeps its own runner, so a job in a local copy stays local. `formatStatus` warns through `FactoryStatus.codexUnsandboxed`.
- Custom agents: `agents` (global) and `lines[].agents` in the factory file (`CustomAgentSchema` in `src/config.ts`; fixed station names are reserved). `lineAgents` gives a line's agents in run order (global, then the line's); on a line with `performance: true` it puts zero's own reviewer first (`PERFORMANCE_AGENT`, origin `zero`: type review, read, blocking, skills `[zero:performance]`, instructions `agents/performance.md` read from `ZERO_AGENTS_DIR` by `agentInstructionsPath`, never the work copy or the repository), so it runs after security and before the other reviewers and only its verified high/critical findings with confidence 8 or more fail the attempt; `parseFactory` refuses an agent named `performance` on such a line or globally when any line has it on, `loadPackages` refuses a package agent with that name then, and `assignedSkills` adds `zero:performance` after build's configured skills on those lines; `customAgentChain` and `pickAgentEngine` (`src/budget.ts`) choose their engine; `stationEngines` (`src/box/credentials.ts`) includes them. `type` says what they do (`after` and `access` derive from it). `review`, the default: the runner runs them after review and security with `ReviewSchema`, as `AgentRequest.custom` (station `review`, access `read`, recorded under their own name); blocking agents' verified high/critical findings fail the attempt, informative ones only report. `build`: they write, in `buildLoop` after build and before verify, as `AgentRequest.custom` (station `build`, access `write`), with an optional `files` glob list matched against the change without the job's spec files (no match: a `zero.skipped` span, no call); zero commits their work with their name, `ok: false` discards it and fails the attempt, and a plan or budget cut resumes at the same agent (`job.station`). `conflict`: access `write` (refusing `after`, `files`, `blocking: false` and other access); when `runJob`'s merge of the base for a `prRefreshKey` mark leaves conflicts `resolveSimply` does not resolve, `resolveWithAgents` in `runner.ts` writes the fallback mark first, then calls each in `lineAgents` order as `AgentRequest.custom` (station `build`, `ConflictSchema`: per file `resolved` or `returned` with a reason) on the merge redone from the mark's head and `baseCommit`, its conflicted files rewritten with diff3 markers by `diff3Markers` (the helper `resolveSimply` also uses; a file without the three stages of a regular file stays as the merge left it), with `requestBlock`, the spec, each path's conflict blocks (keeping the `|||||||` base section, which the prompt explains as the common base before either side changed it) and the base commits that touched it as data; `judgeResolution` accepts only every path `resolved` and no `conflictMarkers`, and after the commit the branch must contain the base commit and the head, then the mark is resolved and the job resumes at verify without an attempt; anything else discards the work (back to the head) and the next agent or build with `conflictFeedback` follows, and missing instructions only skip the agent. Each call is a `zero.station.<agent>` span with `zero.agent.type: conflict` and `zero.conflicts.files`/`resolved`/`returned`/`outcome`/`reason`, which `renderTrace` shows. All read their instructions from `line.repo` (line agents) or the factory folder (global agents), never from the work copy. `.zero/agents/<station>.md` in `line.repo` adds to a fixed station's instructions (`lineInstructions` in `src/agent.ts`). `agentList`/`addAgent`/`removeAgent` in `app.ts` back `zero agent list|add|remove` (`--tipo`, `--archivos`); `agentList` gives the real running order, and the panel's `/agents` line cards show it through `factoryGuide`.
- `src/catalog.ts` (pure): the agent catalog's checks. Entries are `review`, `build` or `conflict` (`CatalogType`; `addFromCatalog` adds a `conflict` one as a blocking agent without `files`, and `catalogInstructions` uses the conflict template when it brings no instructions). `normalizeLicense` takes only MIT, Apache-2.0, BSD-2-Clause and BSD-3-Clause; `screenAgentText` reads a third party's text (never runs it) for prompt injection, credential requests, network or download commands and installs; `catalogKey` normalizes a source (https only, lowercase host, no query, fragment, trailing slash or `.git`); `acceptFindings` keeps the findings that pass those, repeat no name or source of any entry (rejected ones included) nor a line's agent, `proposed` for a known line with a gap, else `listed`, up to `max`. Entries live in the `agent_catalog` table of `state.db` (`createCatalogEntry`, `listCatalog`, `decideCatalogEntry`); `agentCatalog` in `app.ts` (proposed first) backs `zero agent catalog`, printed by `formatCatalog`. `catalogAddPlan` (checks, writes nothing) and `addFromCatalog` back `zero agent catalog add <id> --line <línea> [--yes]`: it shows the entry and the instructions file, asks through `confirm` (default no, nothing written without a terminal), refuses a rejected or added entry and an existing `.zero/agents/<name>.md`, then adds through `addAgent` with `instructions` (`catalogInstructions`: a header with source, license and review date), appends one block per source to the line repository's `THIRD-PARTY-NOTICES.md` and marks the entry `added` with its line; `rejectCatalogEntry` backs `zero agent catalog reject <id> [--motivo]`. The panel's `/agents` page shows the catalog (`agentsPage`), and POST `/agents/catalog/add` shows `confirmCatalogPage` until the form carries `confirm=1`; `/agents/catalog/reject` rejects. `src/line/recruit.ts`: the recruiter, a fixed `recruit` station (`agents/recruit.md`, access `web`, in `IDLE_STATIONS`, so `scoutSpent` counts it). `recruitPass` runs in the daemon's shared idle run after research and before the packages' stations (`DaemonOptions.recruit`, off in `once` runs), with the night shift's gates (`recruit` and `nightShift` not `off`, hours, no queued or running job, andon, budget, an engine for `recruit`, the rest of `limits.usdPerNight` as its cap) at most once every `recruit.everyDays` days (kv `recruit:last`, `RECRUIT_KEY`). `recruitPrompt` lists each non-package line with its agents, its latest unjam diagnosis's causes and its last 20 rejected proposals, every catalog entry's name and source as never-repeat and the unverified `STARTING_POINTS`, saying web content is data; `recruitRun` stores what `acceptFindings` keeps (at most `recruit.perPass`) and never adds an agent or edits the factory file, whatever the line's autonomy.
- `src/skills.ts`: the owner's Claude Code skills (personal and plugin), the loaded packages' (`<package>:<skill>`) and zero's own (`builtinSkills`, source `zero`, full name `zero:<skill>`, from `skills/` of zero's installation found through `import.meta.url` next to `agents/`, copied into the container image and the box image's context too) assigned per agent (`stations.<agent>.skills`) and per line (`lines[].stations.<agent>.skills`): discovery, resolution, and the per-run staged copy (without `allowed-tools`) that the Claude engine loads as a local plugin, other engines get appended to their instructions, and the box mounts read-only at /skills. `agentSkills` in `app.ts` is the single read-only view (with each SKILL.md's short description) behind the panel's `/agents` cards and the chat's `zero_lines`; each agent span records `zero.skills` and `zero.skills.missing`. Packages' and zero's skills resolve by full name only. Zero ships `zero:performance` (`skills/performance/SKILL.md`): a checklist of controls `PERF-NN`, each with `Detect`, `Fix` and `Sources` lines whose https links are only official documentation (web.dev, MDN, Next.js, React, PostgreSQL, Django, Rails, Express, Node.js, Vite, Chrome); `test/skills.test.ts` parses it and checks the required topics (pagination, indexes, N+1, caching, static files and CDN, images, code splitting, background work) and the allowed hosts. `agents/build.md` carries the matching rule not to introduce those problems.
