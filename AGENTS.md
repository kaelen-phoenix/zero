# zero

A software factory that runs on its owner's machine. Agents of any vendor work on this repo, so keep this file accurate. `CLAUDE.md` only points here.

## Commands
- `npm run typecheck`: TypeScript, strict, including tests
- `npm test`: Vitest (`test/`); uses real git in temp repos and fake agents, never a model
- `npm run build`: compiles `src/` to `dist/` (the MCP server and the daemon run from `dist/cli.js`)
- `npx openspec validate --all`: specs and changes under `openspec/`

## Layout
- `src/cli.ts`: commands. `src/app.ts`: operations shared by the CLI, the MCP server and the daemon (request, status, answer, stop, briefing, trace). Never duplicate logic between interfaces; add it here.
- `src/config.ts`: `zero.factory.yaml` schema, effective level. `src/signature.ts`: zero in the loop's signature (`signature` in the file, global or per line, resolved by `lineSignature`): `withTrailer` on every factory commit (spec, attempts, integration merge), `signText` on pull request bodies (`deliveryBody`), and `signedIssues`/`signedMerges`, with which the daemon wraps its real GitHub adapters per line (each pass hands its api factory the line), so issues and comments end with the text before FACTORY_MARK. `src/init.ts`: `zero init`, `zero line add`. `src/home.ts`: `ZERO_HOME` layout.
- `src/budget.ts`: the single answer to "can the factory start more work?". Subscription plans are limited by their usage windows, read from each agent call's span (`quotaAttrs` in `src/agent.ts`); per-use billing by the dollar caps, each engine on its own. `pickEngine` chooses each call's engine from the station's chain (`stationChain` in `src/config.ts`: its engine, then the owner's `fallback` list); the factory pauses only when a line station has every engine of its chain paused. Engines report plan usage as `EngineResult.quota`.
- `src/state/store.ts`: SQLite state (jobs, spans, kv). `src/telemetry/`: tracer and the single definition of every metric.
- `src/line/`: the production line. `runner.ts` is the state machine (checkpoints, attempts, policy). Each station has a module (`spec`, `verify`, `review`, `integrate`); `security` reuses `review.ts` with its own instructions. `automerge.ts` merges pull requests of `autoMerge` lines once GitHub reports them ready (polled by the daemon). `policy.ts` is the only place that decides when the owner is asked. `finish.ts` is the only way a job ends.
- `src/line/scout.ts`: the night shift. While the factory is idle (no queued or running jobs, andon off, budget left, inside the optional `nightShift.hours`), the daemon runs `scoutPass` in the background: the read-only `scout` station (`agents/scout.md`) looks at each line once per period (the day, or the window) and zero keeps only the proposals that pass `filterProposals` (no protected paths, no new credentials, no repeated titles, at most 3). On per-use billing the scout spends at most `limits.usdPerNight` per period. Proposals live in the `proposals` table of `state.db`. `approveProposal`/`rejectProposal` in `app.ts` decide them; approving opens a normal job with source `{kind: 'night-shift'}`. Each stored proposal gets `proposalAutonomy` (the line's `lineAutonomy`, restricted by `research.autonomy` for research-born third-party proposals: scout's `thirdParty` flag or a manifest matched by `touchesManifest` in `policy.ts`). Under `build`/`auto`, and below `nightShift.maxAutoJobsPerDay` across lines (`autonomousJobsSince`), scout approves it itself: a job with source `{kind: 'night-shift', proposal, autonomy}` and the proposal's `decidedBy: 'night-shift'`. The runner parks `build` jobs (and `auto` research-born jobs whose diff touches a manifest, unless research is `auto`) at `before-integrate` with onTimeout `reject` (`nightShiftHold`); `approveProposal` then answers that job and `rejectProposal` stops it. The daemon considers owner jobs first (`ownerFirst`) and starts an autonomous job only when nothing else is queued or running. Rejections go to the line's townhall with the owner's reason, and scout's prompt lists the line's last 20 rejected or reverted proposals (`recentRejected`). Per line, `scoutIssues` lists through `IssueApi.unlabeled` the open unlabeled issues written by writers (TRUSTED) not yet linked by a proposal (at most 20, newest first) as data in scout's prompt; a proposal's `issue` is kept as `sourceIssue`/`sourceIssueUrl` only when it was listed. At the start of each `scoutPass` (after the off/hours and andon checks), `promotePending` takes on pending proposals of lines now at `build`/`auto` through `takeOnItsOwn` (oldest first, within `maxAutoJobsPerDay`), never third-party ones (`thirdParty` or `touchesManifest`). `ownerOnly` keeps a proposal at `propose` whatever the autonomy: born from a business note (`business`), flagged `commercial` by scout (license, pricing, charges, payments, legal text) or with paths matched by `touchesLegal` in `policy.ts`; `nightShiftHold` also holds any autonomous job whose changed files match `touchesLegal`. The briefing and the panel's Investigación tab split notes into "Negocio" and "Técnica".
- `src/line/reverts.ts`: `detectReverts` (a daemon pass on the intake interval) marks `reverted` the night-shift proposals whose job integrated on its own (no `approvals.integrate`; delivery mode `merge` with a commit, or `pull-request` with the merge or squash commit that `automerge.ts` or the pass itself records from GitHub's `mergeCommitSha`) once the base branch (local, or `<remote>/<base>` after a fetch on pull-request lines) has a `This reverts commit <sha>` commit or, for pull requests, GitHub's `Reverts owner/repo#N`, and posts a `propuesta revertida` lesson to the line's townhall.
- `src/line/research.ts`: the research station (`agents/research.md`, access `web`: on Claude the read tools plus `WebSearch`, elsewhere like `read`). While the factory is idle the daemon runs `researchPass` with the night shift's gates; only lines with a line-level research skill (`lines[].stations.research.skills`) research. Each (line, skill) pair runs once per local day (kv `research:<line>:<skill>`), with a prompt naming that single skill and at most `research.perLinePerDay` notes of its own, least recently researched first. Skills listed in `lines[].stations.research.business` (`businessSkills` in config.ts; names not in `skills` are ignored) write business notes (`skill`, `business` on the note). Notes (http(s) sources only, local paths scrubbed by `sanitizeNotes`) live in the `research_notes` table; scout's prompt gets its line's notes of the last 7 days as data. `scoutSpent` counts scout and research, which share `limits.usdPerNight`. `requestFromResearchNote` in `app.ts` opens a job with source `{kind: 'research'}`. `research.autonomy` caps research-born third-party proposals (see `proposalAutonomy` in scout.ts); scout's output carries `researchNote` (kept only when it is one of the line's notes in the prompt) and `thirdParty`.
- `src/daemon.ts`: background loop. `src/mcp/server.ts`: chat tools. `src/install.ts`: client registration.
- `src/agent.ts` + `src/engines/`: engine-agnostic agent runner and one adapter per engine. `agents/*.md` holds the per-station instructions, shared by every engine.
- Custom agents: `agents` (global) and `lines[].agents` in the factory file (`CustomAgentSchema` in `src/config.ts`; fixed station names are reserved). `lineAgents` gives a line's agents in run order (global, then the line's); `customAgentChain` and `pickAgentEngine` (`src/budget.ts`) choose their engine; `stationEngines` (`src/box/credentials.ts`) includes them. For now they are read-only reviewers: the runner runs them after review and security with `ReviewSchema`, as `AgentRequest.custom` (station `review`, access `read`, recorded under their own name), reading their instructions from `line.repo` (line agents) or the factory folder (global agents), never from the work copy. Blocking agents' verified high/critical findings fail the attempt; informative ones only report. `.zero/agents/<station>.md` in `line.repo` adds to a fixed station's instructions (`lineInstructions` in `src/agent.ts`). `agentList`/`addAgent`/`removeAgent` in `app.ts` back `zero agent list|add|remove`.
- `src/skills.ts`: the owner's Claude Code skills (personal and plugin) assigned per agent (`stations.<agent>.skills`) and per line (`lines[].stations.<agent>.skills`): discovery, resolution, and the per-run staged copy (without `allowed-tools`) that the Claude engine loads as a local plugin, other engines get appended to their instructions, and the box mounts read-only at /skills. `agentSkills` in `app.ts` is the single read-only view (with each SKILL.md's short description) behind the panel's `/agents` cards and the chat's `zero_lines`; each agent span records `zero.skills` and `zero.skills.missing`.
- `src/townhall/`: collective memory and the owner briefing.
- `src/box/`: the isolation box. `runtime.ts` detects Podman/Docker, `status.ts` inspects and caches readiness, `image.ts` and `box/Dockerfile` build the image, `run.ts` holds every hardening flag, `executor.ts` routes shell commands and agents into the box, `agent.ts` is the entry point inside it, and `setup.ts` walks the per-platform plan with consent. `src/keychain.ts` stores credentials in the OS keychain.
- The egress gate: boxes run on an internal network with no DNS and leave only through zero's proxy. `src/box/egress.ts` holds the rules (pure), `gate.ts` is the proxy (runs in its own container via `gate-main.ts`), and `network.ts` starts it, issues one pass per box run and moves its records into `state.db`. Only `suspicious` refusals affect a job.
- `src/intake/github.ts`: GitHub issues as requests (polled by the daemon). Only issues written and labeled by people with write access; the issue hears back per job status. `src/intake/comments.ts` answers later comments from people with write access through the read-only `reply` station (no repository; zero computes where the change is), which may open a follow-up job or answer a waiting question. Factory comments carry `FACTORY_MARK`, since they are posted as the owner. Pull-request lines start each job from the remote's base (`startingBase` in the runner). `src/intake/proposals.ts` mirrors night-shift proposals as issues on every GitHub line, whether or not it takes issues: `syncProposalIssues` (its own daemon pass) publishes them with the label `zero:propuesta` (never the work label), scrubbing secrets and the owner's paths, and tells the issue once about a decision taken in the factory (approval: comment plus work label, recording the issue state first so the intake opens no second job; rejection: comment plus close). `deliveryBody` closes the proposal's issue. On proposals whose `proposalAutonomy` is `propose`, the sync also reads each issue (`IssueApi.issue`): the work label applied by a writer approves through `approveProposal`, closing it without the label (by a writer) rejects through `rejectProposal`; elsewhere the issue is a record, and the sync closes it as completed once a non-PR delivery lands (`issueClosed`). `takeIssues` skips `zero:propuesta` issues (`PROPOSAL_LABEL` lives in `keys.ts`). `src/intake/research.ts`: `syncResearchIssues` (run right after `syncProposalIssues` in the same daemon pass) publishes each research note once as a `zero:investigacion` issue, scrubbed with `scrubLocal` and with @mentions broken (`breakMentions`).
- `src/panel/`: the control panel the daemon serves on 127.0.0.1. `server.ts` (session from the key in the link's fragment, Origin checks, actions through `app.ts`), `html.ts` (server-rendered pages, including the production line view at `/line`, which refreshes its rows from a fragment pushed on the `/line/events` stream, polling as a fallback, the read-only `/about` and `/agents` pages built from `factoryGuide` in `app.ts`, the `/proposals` tab built from `proposalsView` in `app.ts`, whose approve button only shows a confirmation page until the form carries `confirm=1`, and the `/research` tab built from `researchView`, whose "Pedir trabajo" button confirms the same way before `requestFromResearchNote`), `key.ts` (key in the keychain), `tunnel.ts` (optional cloudflared quick tunnel, downloaded with consent and kept by the daemon).
- `openspec/`: specs (`specs/`) and changes (`changes/`). `docs/adr/`: decisions.

## Conventions
- ESM, Node 22, imports with the `.js` suffix. What zero shows the owner (CLI, panel, chat) is in Spanish; code, comments and agent instructions are in English.
- The README is kept in both languages: English in `README.md` and Spanish in `README.es.md`, with the same structure and the same code blocks (`test/docs.test.ts` checks it). Every documentation change is made in both; what zero shows the owner (CLI, panel, chat) stays in Spanish.
- Engine-specific behaviour stays in `src/engines/`; nothing else may assume a vendor.
- Guarantees are enforced by zero, never trusted to an engine: read-only stations, timeouts, schema validation, verify gate, protected paths, citation checks, isolation box, egress gate.
- The chat may only tighten egress rules (block); allowing a site or changing the mode is for the owner on the terminal or in the file.
- Nothing installs software or needs admin without the owner's explicit consent. Secrets never go in argv, files or logs.
- The line never blocks on the owner: questions park a job, carry a timeout and a default answer, and approvals resume from a checkpoint.
- Every job end goes through `finalizeJob`, so it gets a final status, a closed job span and a townhall report.
- The townhall must never break production: store failures are logged, not thrown.
- Behaviour changes start as an OpenSpec change under `openspec/changes/`.
