# zero

A software factory that runs on its owner's machine. Agents of any vendor work on this repo, so keep this file accurate. `CLAUDE.md` only points here.

## Commands
- `npm run typecheck`: TypeScript, strict, including tests
- `npm test`: Vitest (`test/`); uses real git in temp repos and fake agents, never a model
- `npm run build`: compiles `src/` to `dist/` (the MCP server and the daemon run from `dist/cli.js`)
- `npx openspec validate --all`: specs and changes under `openspec/`

## Layout
- `src/cli.ts`: commands. `src/app.ts`: operations shared by the CLI, the MCP server and the daemon (request, status, answer, stop, briefing, trace). Never duplicate logic between interfaces; add it here.
- `src/config.ts`: `zero.factory.yaml` schema, effective level, `commitAuthor` (global and per line: `zero` or `owner`; with `owner`, `authorEnv` in `src/workspace.ts` passes the line repo's git config identity as GIT_AUTHOR_* to work-copy commits and merge-mode integration, zero stays the committer and is the author when no identity is configured). `src/signature.ts`: zero in the loop's signature (`signature` in the file, global or per line, resolved by `lineSignature`): `withTrailer` on every factory commit (spec, attempts, integration merge), `signText` on pull request bodies (`deliveryBody`), and `signedIssues`/`signedMerges`, with which the daemon wraps its real GitHub adapters per line (each pass hands its api factory the line), so issues and comments end with the text before FACTORY_MARK. `src/init.ts`: `zero init`, `zero line add`. `src/home.ts`: `ZERO_HOME` layout (`drills` holds the regeneration drills, `packageData` the packages' data folders and `packageRepos` their local git repositories). `src/autostart.ts`: `syncAutostart` makes the user-level login entry for this ZERO_HOME (a `zero-<hash>.cmd` in the Windows Startup folder, a LaunchAgent, a systemd user unit) exist exactly when `autostart` (top level of the factory file, default false, never changed by a chat tool) is on; nothing in a container. `setAutostart` in `app.ts` backs `zero autostart on|off`, and the daemon syncs it at start and when a reload changes it.
- Docker: `docker/Dockerfile`, `compose.yaml` (no socket, no credentials) and `docker/compose.box.yaml` (the only one mounting the socket, data at the same path inside and out); `docs/adr/0003-fabrica-en-docker.md` has the decisions. `ZERO_CONTAINER=1`, read only through `inContainer` in `src/home.ts`, changes three things. `SecretStore` (`src/keychain.ts`, `defaultKeyring`) stores in `secrets.enc` (`encryptedFileKeyring`, AES-256-GCM, key in `ZERO_MASTER_KEY_FILE`, by default the Docker secret `zero_master_key`, nothing written without a key that opens the file) and reads Docker secrets (`ZERO_SECRETS_DIR`) between the environment and the store. The daemon starts no jobs or idle passes while the box is not ready (`waitsForBox` in `app.ts`) instead of moving to local copies. Engines outside the box get their credential only in their own process (`EngineRequest.env`, `localCredentials` in `src/agent.ts`, given `secrets` by the daemon). `githubToken` also reads `GH_TOKEN` from the store, and `zero git-credential get` hands it to git for github.com. `panel.host` in the factory file (default 127.0.0.1) is where the panel listens.
- `src/setup.ts`: `zero setup` (`runSetup`, every terminal and machine access injected through `SetupDeps`): modes, engines (its `ENGINES` table holds each CLI's login and credentials), limits, isolation, panel, GitHub and, outside a container, the start at login (`autostart`, registered through `SetupDeps.syncAutostart`); it refuses without a terminal, installs nothing and writes through `initFactory` and `editFactory`, so it can run again.
- `src/budget.ts`: the single answer to "can the factory start more work?". Subscription plans are limited by their usage windows, read from each agent call's span (`quotaAttrs` in `src/agent.ts`); per-use billing by the dollar caps, each engine on its own, and for 15 minutes (`UNKNOWN_RESET_MS`) after a call refused because the API key ran out of credit (`Credit balance is too low`, marked `limited` by `claudeResult` and `claudeThrown` in `src/engines/claude.ts`). A subscription the SDK refuses with only a text (`You've hit your session limit · resets 5am`, with no rejected rate-limit event when the plan was used up outside the factory) is marked `limited` the same way, by `refusedQuota`, read only from failed calls: the job waits in the queue (`quotaStop`) and the engine pauses for `UNKNOWN_RESET_MS` at a time instead of failing the work. `pickEngine` chooses each call's engine from the station's chain (`stationChain` in `src/config.ts`: its engine, then the owner's `fallback` list); the factory pauses only when a line station has every engine of its chain paused. Engines report plan usage as `EngineResult.quota`.
- `src/install-freshness.ts`: how far the installed copy of zero (`installRoot`, the folder holding the running dist/cli.js) is from what was merged. `checkInstall`, a daemon pass on the intake interval (`DaemonOptions.install` injects the folder and the `GitRunner`; off in `once` runs without it), asks git at most once an hour and stores kv `install:freshness` (`InstallFreshness`: `checkedAt`, `behind` against the upstream or `<remote>/<branch>` after a best-effort fetch, `staleBuild` when a file under `src/` is newer than `dist/cli.js`, `repository` when the remote is on GitHub, or only a `problem` for a folder that is not the root of a git repository). While `installBehind`, `factoryStatus` sets `FactoryStatus.install` and `installLine` in `src/format.ts` gives the `Instalación atrasada` line of `formatStatus` and the panel summary; the briefing gets an `## Instalación` section.
- `src/state/store.ts`: SQLite state (jobs, spans, kv). `src/telemetry/`: tracer and the single definition of every metric; `otlp.ts` is the optional OTLP/HTTP JSON export (`telemetry.otlp` in the factory file, header values as secret names resolved through `SecretStore`), a daemon pass that sends finished jobs after a kv cursor (`otlp:cursor`), scrubs with `scrubLocal` and retries a batch at most 5 times.
- `src/line/`: the production line. `runner.ts` is the state machine (checkpoints, attempts, policy). Each station has a module (`spec`, `verify`, `review`, `integrate`); `security` reuses `review.ts` with its own instructions. Once a spec is valid and feasible, and before anything is written, `specStation` passes it through `uniqueRequirementNames` (`src/line/spec.ts`): a requirement name repeated in the request or in `existingRequirementNames` (the capability's main spec and other unarchived changes' deltas, compared like openspec's fold) gets the suffix ` (<job id>)`, then ` (<job id>-<n>)`, so `openspec archive` does not fail with `already exists` and no extra model call is spent. It only sees the work copy, so two unintegrated jobs can still repeat a name. A spec may carry `stages` (at least 2 and at most `MAX_STAGES`, checked by `specProblems`; `specStages`, `jobStage`): `buildLoop` runs build, the writing agents and verify per stage, records `stagesDone` on the job (resetting attempt and feedback) when a stage passes verify, so a cut or failed later stage is rebuilt alone on the earlier commits, and runs dependencies and the reviewers once after the last; `maxAttempts` counts per stage. `describeJobStatus` and the panel's `LineRow.stage` show `etapa n de N`. `automerge.ts` merges pull requests of `autoMerge` lines once GitHub reports them ready (polled by the daemon); a blocked one keeps `backoff` in its `MergeState` and, with the same head and `mergeable`, is asked only for `pullRequest` until the wait (5 minutes doubling up to 60) ends. A pull request with `mergeable: false` (or a head whose `updateBranch` answered a merge conflict, `MergeState.conflict`) goes back to the queue through `takeBack` when the job has a spec, the pull request used fewer than `MAX_RESOLUTIONS` (2) conflict resolutions in its life (`MergeState.resolutions`, not the build's attempts; the job goes back with `attempt` at most `maxAttempts - 1`), its local branch is at the head, that head was not tried (`MergeState.resolving`, kept by every write) and the base fetches; otherwise it is told as blocked with `en conflicto con la rama base` and, when the resolutions are used up or that head's resolution failed, what is missing. `mergeDecision` decides the conflict before any check, and a head in conflict gets no `checks`, `behind`, `updateBranch`, rerun, outage or billing handling. A head with failed checks that GitHub does not call mergeable is tested locally first (`conflictsLocally`: fetch of the base, `git merge-tree --write-tree` in the line's repository); a conflict found there is recorded as `MergeState.conflict` and goes through `takeBack` before any check handling. When failed checks (no billing refusal, no outage, every check of the tip ended) have nothing left in `unblock` (base not ahead or `MAX_REFRESHES` used, runs already rerun at this tip), `fixChecks` puts the job back in the queue to fix them on its own branch (checkpoint `spec`, station `build`, `attempt` 0, `approvals.integrate` dropped), with `checksFeedback` as its feedback (each failed check's name, the tests `failedTests` finds in its `failedLog` and the end of that log, `FIX_LOG_CHARS`, through `scrubLocal`, framed as CI data) and the prRefreshKey mark with `checks` (that feedback, already `started`): `runJob` merges no base, `buildLoop` keeps the checks in the prompt and fails an attempt that leaves the branch at the head, `updateProblem` only asks for the earlier head, and the push goes to the same pull request; a failed fix ends `delivered` like a failed resolution. Its own limit is `MergeState.fixes` (at most `MAX_CHECK_FIXES`, 2) and each tip is tried once (`MergeState.fixing`), both kept by every save; a busy repository makes it wait its turn, and a used-up limit or a failed tip is told with `fallaron los checks …` and `zero reintentar <job>`. A job without a spec, a branch not at the head, a pending cleanup or a base that does not fetch is left as it is. The kv mark `prRefreshKey` (`src/line/finish.ts`) drives the update: `runJob` runs `WorkCopy.mergeBase` on the base commit it pins in the mark (`baseCommit`, since `origin/<base>` is shared and moves during the job; a clean merge resumes at verify with no attempt spent; a conflict goes to build as an attempt, `buildLoop` restarting the merge from the head before every engine call and refusing what `conflictMarkers` finds or a branch without the base), checks again before integrating, and `integrate` with `existing` compares `ls-remote` with the head and pushes without force, opening nothing. With the mark, `finalizeJob` turns `failed` or `stopped` into `delivered` with the original delivery, moves the branch back to the head and posts a `blocker`. `mergeRequested` in `automerge.ts` (behind `mergePullRequest` in `app.ts`, `zero fusionar <trabajo | url>` and the chat's `zero_merge`, with an injectable `MergeApiFactory`; the real one is the line's signed `githubMerges` outside the meter) merges a delivered pull request on request, with or without `autoMerge`, only when `mergeDecision` says `merge`; otherwise it returns `merged: false` with why and writes nothing to GitHub, and a refused merge call comes back the same way. A merge records a `zero.merge` span (`zero.merge.via`, `zero.merge.commit`, `zero.merge.url`), MergeState `merged` (so `watchedJobs` drops it) and a `fundido a pedido` townhall lesson, all best effort after the merge. `policy.ts` is the only place that decides when the owner is asked. `finish.ts` is the only way a job ends; a work copy it cannot remove (EBUSY on Windows) never changes the job's end: `finalizeJob` records it as kv `cleanup:<job>` (`src/line/cleanup.ts`), the daemon's `retryCleanups` pass (`cleanupPass`, on the intake interval) tries again and deletes the record once it goes (never while that job is at work again in the same folder, and `takeBack` leaves a pull request in conflict for later while its job has one), and `zero status` shows `Limpiezas pendientes:` meanwhile. A passing network cut that reaches `runJob`'s final catch (`isTransientNetworkError`: ECONNRESET, ETIMEDOUT, EAI_AGAIN, ECONNREFUSED or EPIPE in the `code` or message of the error or its causes) puts the job back in the queue from its checkpoint, at most 2 times in its life (kv `network-retry:<job>`): uncommitted changes are dropped and a cut build does not spend an attempt. A locked folder (`isLockedFolderError`: EBUSY the same way) is handled alike, at most 2 times (kv `busy-retry:<job>`), after killing what was left in the work copy (`RunnerDeps.killLeftovers`); the daemon also kills the leftovers in each interrupted `running` job's copy before re-queuing it (`DaemonOptions.killLeftovers`), and `mergeIntoBase` never fails over its temporary `merge-<job>` folder: a locked earlier one is replaced by a fresh name and one it cannot remove after the merge is recorded as `cleanup:<job>-merge` (`IntegrateOptions.onLeftover`). Anything that fails while first preparing the work copy (`SetupFailed`) is never retried, since a resumed job would skip setup. A 422 `already exists` when opening a pull request ends in `integration-blocked`. Before leaving a pull request blocked by failed checks, `unblock` in `automerge.ts` tries what needs no code change, through the optional `MergeApi.behind`/`updateBranch`/`rerun`: behind its base, GitHub merges the base in (`MergeState.refreshes`, at most `MAX_REFRESHES` in its life; `refreshing` holds the repository so its pull requests are refreshed one at a time, for at most 2 hours, and the others wait blocked with `espera su turno`, looked at every 5 minutes), then `followRemoteTip` fetches the new tip into the line's local branch; up to date, the failed GitHub Actions runs (`Check.run`, from `actionsRun`) are run again once per tip (`MergeState.rerun`), which holds the repository the same way (`refreshing.rerun`, until every check of the tip ended) and waits its turn the same way. Nothing is started for a pull request with a failed check while another of its checks still runs (it waits with `esperando los demás checks`, and a hold is only released once every check of the tip ended), nor while another watched pull request of the repository delivered in the last 2 hours is still `waiting` for its first checks (`firstChecksElsewhere`, read from kv): CI that shares an environment keeps one run waiting and cancels the rest. A GitHub that refuses changes nothing, and limits are rethrown. A shared environment that is down is told from a change (`ChecksOutage`, kv `checksOutageKey`): the failed checks of each tip are remembered for 24 hours (kv `checksFailuresKey`, with `Check.at`, the time GitHub says it ended; failures without one are never compared in time), and the same check failed in two watched pull requests of the repository at most `OUTAGE_WINDOW_MS` apart, or also failed at the tip of the base branch (read with `checks(base)` right before an update or a rerun, a base that cannot be read saying nothing), records the outage. While it lasts a pull request failing one of its checks is left `blocked` with `outageWhy`, marked `MergeState.outage`, without comment, update or rerun. After the pull requests, `followOutage` (end of `pollMerges`) forgets an outage no marked pull request is left for, ends it when one of its checks ended well after its `lastFailure` at a watched tip or at the base (read at most every 5 minutes, `baseLookAt`), recording kv `checksRecoveredKey` so failures that ended before then count for nothing (neither between pull requests nor at the base), and clears the marked pull requests' `backoff`; otherwise, from `nextProbeAt` (30 minutes after the last failure, doubling per failed probe up to 240) and with the repository free, it probes by running the failed runs of the oldest marked pull request again (`ChecksOutage.probe`, `refreshing` with `rerun` so `holds` keeps the repository, its own `MergeState.rerun` untouched). Once it is over, each marked pull request gets one more rerun even with `rerun` at its tip, one at a time, which clears its mark. `factoryStatus` reports each outage under way as `outages` (kv `checks-outage:<repo>`, with the pull requests whose `MergeState.outage` is its `since`) and leaves those out of `merges`, so `formatStatus`, the panel's summary and the briefing show one `Entorno caído en <repo> desde HH:MM (checks: …)` line per outage (`outageText` in `automerge.ts`, shared with `outageWhy`; `outageLine` in `src/format.ts`) instead of one per pull request. A failed check run GitHub never started over the account's billing (`billingRefusal` on its output or, when it has them, its annotations, marking `Check.billing`; `Check.started` is the run's `started_at` once in progress or completed) holds its pull request before any outage logic: no comment, refresh, rerun or failure record, `MergeState.billing` (kept by every save, like `billingRerun`), `blocked` with `billingText` and a backoff, and one kv `checks-billing:<repo>` record per repository (`ChecksBilling`: `since`, `last`, `jobs`) that `factoryStatus` lists as `billing` (its pull requests left out of `merges`) and `formatStatus` (`billingLine`), the panel's summary and the briefing show once. After the outages, `followBilling` (end of `pollMerges`) waits for a non-billing check `started` after the record's `last` at a watched tip or at the base (read at most every 5 minutes), records it as `recovered` (a later refusal clears it), then with the repository free reruns the refused runs of the oldest held pull request, one per pass and each run once in its life (`billingRerun`), clearing its mark and holding the repository with `refreshing.rerun`; a pull request refused again on runs already rerun is only told, and the record goes once it holds none.
- `src/line/verify.ts`: the verify station. `operationArtifacts` holds the shapes of the factory's operation output (added files only, minus the line's `allowedArtifacts` and the Markdown of the job's own specification), including regeneration drill output (everything under a `drills/<id>/` folder holding an added `informe.md` or `resultado.json`, and that pair added in the same folder anywhere, found over all added files, allowed ones included); `verifyChange` runs it before protected paths and commands, failing the attempt, and `runJob` runs it again over the whole change just before integrating, failing the job. Each verify command's time limit comes from `verifyTimeoutMs` in `src/line/pace.ts`: the line's `verifyTimeoutMinutes` (20 when absent) and never less than twice the slowest of its last 5 passing runs on that line in 30 days (read from the `zero.verify.command` spans, `zero.run_ms` when present; history alone gives at most 4 hours); a command over its limit says the limit and the option in its feedback. A command that fails with output that reads like the machine and not the change (`machineTrouble` in `verify.ts`: a test over its own timeout, no memory, EBUSY, a dead worker, a network cut) is run once more before the attempt fails (`zero.verify.machine` on the failed span, `zero.verify.again` on the second). The same file holds `localCommands`, the queue through which the runner's local `shell` (setup and verify outside the box) lets `commandConcurrency` commands run at once across jobs; waiting does not count against the time limit, and an aborted wait never runs. `prepareWorkCopy` tries a failed first preparation once more in a fresh copy (`SETUP_TRIES`) before `SetupFailed`.
- `src/line/dependencies.ts`: the dependency check, off unless a line sets `checkDependencies`. After verify and before the reviewers, `buildLoop` runs `newNpmDependencies` (changed package.json and package-lock.json read with `git cat-file blob` at HEAD and at the merge base, up to `MAX_MANIFEST_BYTES`, a HEAD manifest that cannot be read or parsed counting as `unreadable` and reaching security as unverified; lock entries resolved outside `https://registry.npmjs.org/` and non-registry specs are left out) and `checkDependencies` (OSV querybatch and deps.dev from zero's process through `RunnerDeps.fetch`, 10 s per request). A `MAL-` advisory, a 404 on deps.dev or an invalid name fails the attempt; recent (under 7 days) or first versions and unverified packages (any request failure, never thrown) reach only the security prompt through `dependencyBlock`.
- `src/line/scout.ts`: the night shift. While the factory is idle (no queued or running jobs, andon off, budget left, inside the optional `nightShift.hours`), the daemon runs `scoutPass` in the background: the read-only `scout` station (`agents/scout.md`) looks at each line once per period (the day, or the window) and zero keeps only the proposals that pass `filterProposals` (no protected paths, no new credentials, no repeated titles, at most 3). On per-use billing the scout spends at most `limits.usdPerNight` per period. Proposals live in the `proposals` table of `state.db`. `approveProposal`/`rejectProposal` in `app.ts` decide them; approving opens a normal job with source `{kind: 'night-shift'}`. Each stored proposal gets `proposalAutonomy` (the line's `lineAutonomy`, restricted by `research.autonomy` for every proposal with a `researchNote`, whatever scout's `thirdParty` flag or its paths say; `proposalRequest` in `app.ts` states the note in the job's request as web data, not instructions). Under `build`/`auto`, and below `nightShift.maxAutoJobsPerDay` across lines (`autonomousJobsSince`), scout approves it itself: a job with source `{kind: 'night-shift', proposal, autonomy}` and the proposal's `decidedBy: 'night-shift'`. The runner parks `build` jobs (and `auto` research-born jobs whose diff touches a manifest, unless research is `auto`) at `before-integrate` with onTimeout `reject` (`nightShiftHold`); `approveProposal` then answers that job and `rejectProposal` stops it. The daemon considers owner jobs first (`ownerFirst`) and starts an autonomous job only when nothing else is queued or running. Rejections go to the line's townhall with the owner's reason, and scout's prompt lists the line's last 20 rejected or reverted proposals (`recentRejected`). Per line, `scoutIssues` lists through `IssueApi.unlabeled` the open unlabeled issues written by writers (TRUSTED) not yet linked by a proposal (at most 20, newest first) as data in scout's prompt; a proposal's `issue` is kept as `sourceIssue`/`sourceIssueUrl` only when it was listed. At the start of each `scoutPass` (after the off/hours and andon checks), `promotePending` takes on pending proposals of lines now at `build`/`auto` through `takeOnItsOwn` (oldest first, within `maxAutoJobsPerDay`), never third-party ones (`thirdParty` or `touchesManifest`). `ownerOnly` keeps a proposal at `propose` whatever the autonomy: born from a business note (`business`), flagged `commercial` by scout (license, pricing, charges, payments, legal text) or with paths matched by `touchesLegal` in `policy.ts`; `nightShiftHold` also holds any autonomous job whose changed files match `touchesLegal`. The briefing and the panel's Investigación tab split notes into "Negocio" and "Técnica".
- `src/line/reverts.ts`: `detectReverts` (a daemon pass on the intake interval) marks `reverted` the night-shift proposals whose job integrated on its own (no `approvals.integrate`; delivery mode `merge` with a commit, or `pull-request` with the merge or squash commit that `automerge.ts` or the pass itself records from GitHub's `mergeCommitSha`) once the base branch (local, or `<remote>/<base>` after a fetch on pull-request lines) has a `This reverts commit <sha>` commit or, for pull requests, GitHub's `Reverts owner/repo#N`, and posts a `propuesta revertida` lesson to the line's townhall. A pull request GitHub reports closed without merging is asked about again only 24 hours later (`reverts:closed:<job>` in kv, an ISO date), since it can be reopened and merged; the date goes when it is seen open or merged with a commit, and a store failure only means asking as usual. Errors from GitHub open no wait.
- `src/line/drill.ts`: the regeneration drill behind `zero simulacro <line> <capability> --archivos <glob>... [--usd N] [--conservar]` (`regenerationDrill` in `app.ts`, which refuses before creating anything: unknown line, `isolation: container`, andon, `budgetState` reached, `--usd` not positive or above `limits.usdPerJob`, no `verify`, no `openspec/specs/<capability>/spec.md` at the base branch, `<ZERO_HOME>/drills` inside a line's or the current folder's repository (`versionedAt`, shared with `saveReport`), no file left by `drillFiles`). `runDrill` clones the base branch with `--no-hardlinks --no-local` into `<ZERO_HOME>/drills/<id>/copy`, removes the matched tracked files (never tests, `isTestFile`, nor `openspec/`), replaces `.git` with a fresh one-commit repository, runs `setup`, makes one `build` call (`pickEngine`, `maxBudgetUsd`, `DrillOutput` with `missing`), runs `verify` (20 minutes each) and writes `informe.md` and `resultado.json` next to the copy, which it then removes in a `finally` (`DrillDeps.removeCopy`; a failure is only logged) unless `keep` (`--conservar`) asks to keep it; `DrillResult.copyKept` and the report's `Copia de trabajo:` line say which. Outcome: `inválido` when a test or spec differs from the copy's commit, `alcanzan` when every file came back, verify passed and the agent ended ok without its cap, else `no alcanzan`.
- `src/line/research.ts`: the research station (`agents/research.md`, access `web`: on Claude the read tools plus `WebSearch`, elsewhere like `read`). While the factory is idle the daemon runs `researchPass` with the night shift's gates; only lines with a line-level research skill (`lines[].stations.research.skills`) research. Each (line, skill) pair runs once per local day (kv `research:<line>:<skill>`), with a prompt naming that single skill and at most `research.perLinePerDay` notes of its own, least recently researched first. Skills listed in `lines[].stations.research.business` (`businessSkills` in config.ts; names not in `skills` are ignored) write business notes (`skill`, `business` on the note). Notes (http(s) sources only, local paths scrubbed by `sanitizeNotes`) live in the `research_notes` table; scout's prompt gets its line's notes of the last 7 days as data. `scoutSpent` counts what scout, research and the packages' stations were really charged (`billedUsd` in `budget.ts`, like `jobBilledUsd`: subscription calls do not count, unknown billing does), since they share `limits.usdPerNight`; the daemon runs them one after the other in a single shared idle run (`idlePasses`: scout, then research, then the packages' stations), so each pass computes its cap after the other's spend is recorded. `requestFromResearchNote` in `app.ts` opens a job with source `{kind: 'research'}`. `research.autonomy` caps every research-born proposal (see `proposalAutonomy` in scout.ts); scout's output carries `researchNote` (kept only when it is one of the line's notes in the prompt) and `thirdParty`.
- `src/line/unjam.ts`: the unjam station (`agents/unjam.md`, access `read`, cwd `line.repo`). `unjamPass` runs in the daemon's shared idle run after scout and before research, with the night shift's gates (`unjam` not `off`, hours, andon, no queued or running job, budget, an engine for `unjam`, the rest of `limits.usdPerNight` as each call's cap; `unjam` is in `IDLE_STATIONS`, so `scoutSpent` counts it), once per line per period (kv `unjam-pass:<line>`) and never for a line without jams. `collectJams` gathers a line's jams from its records alone (failed jobs of the last 7 days with their feedback, waiting jobs, blocked auto-merge pull requests with `conflict` from `backoff.mergeable: false`, the repository's `checks-outage:`/`checks-billing:` records, intake problems, pending cleanups, a box that is not ready, and an `install` jam on the line whose GitHub repository is `install:freshness`'s `repository` while `installBehind`), each with an id stable within the pass; `withCheckLogs` adds the end (`LOG_CHARS`) of a failed Actions job's log through the optional `MergeApi.failedLog`, once per repository and check name (GitHub pass `unjam` of the meter; any failure leaves the jam without log). `acceptCauses` keeps causes naming jams of the prompt (at most `CAUSES_PER_LINE`, scrubbed) and `unjamLine` stores them in kv `unjam:<line>` (`Diagnosis`, `readDiagnosis`), each with `seen` (`countSeen`: the earlier diagnosis's same-title cause plus one), then publishes a `traba repetida: <title>` townhall lesson for each cause with 2 jams or `seen` 2 or more (`publishLessons`, a failure only logged). Every unjam proposal's `why` is the diagnosis plus `evidenceText`, computed by zero from the cause's jams (count, jobs, pull request urls, `seen`). `openCapabilities` turns each `capability` cause (target `line` from the lines listed in the prompt) into one unjam proposal on the target line carrying `forJobs` (the `for_jobs` column: the cause's failed jobs whose reason starts with `SPEC_REFUSAL` in `runner.ts`, without a spec, not carried by another pending or approved unjam proposal nor resent), through `takeOnItsOwn` with the target line's autonomy and the same title dedupe; an unknown or package line, or no job refused at spec, makes the cause `none` with a `todo`. `resendAfterCapability` (the daemon's `resendRefused`, on the intake interval) resends each still `failed` job of an approved one once (kv `unjam:resent:<job>` = the new job) through `requestWork` with its request, line and source, after the proposal's job entered (delivered `merge` with a commit, or MergeState `merged`) and, when the target line's repository is `install:freshness`'s `repository`, only with a record checked after that job finished without `problem`, `behind` or `staleBuild`; With Podman the network is made with `--disable-dns` (`networkCreateArgs` in `network.ts`): Podman's own name server resolves nothing outside on an internal network and the gate, started there, would take it for its resolver; a network an earlier version left with it is made again once only this factory's gate is on it. `src/box/egress.ts` holds the rules (pure), `gate.ts` is the proxy (runs in its own container via `gate-main.ts`), and `network.ts` starts it, issues one pass per box run and moves its records into `state.db`. Only `suspicious` refusals affect a job.
- `src/intake/github.ts`: GitHub issues as requests (polled by the daemon). Only issues written and labeled by people with write access; the issue hears back per job status. `src/intake/comments.ts` answers later comments from people with write access through the read-only `reply` station (no repository; zero computes where the change is), which may open a follow-up job or answer a waiting question. Factory comments carry `FACTORY_MARK`, since they are posted as the owner. Pull-request lines start each job from the remote's base (`startingBase` in the runner). `src/intake/proposals.ts` mirrors night-shift proposals as issues on every GitHub line, whether or not it takes issues: `syncProposalIssues` (its own daemon pass) publishes them with the label `zero:propuesta` (never the work label), scrubbing secrets and the owner's paths, and tells the issue once about a decision taken in the factory (approval: comment plus work label, recording the issue state first so the intake opens no second job; rejection: comment plus close). `deliveryBody` closes the proposal's issue. On proposals whose `proposalAutonomy` is `propose`, the sync also reads each issue (`IssueApi.issue`): the work label applied by a writer approves through `approveProposal`, closing it without the label (by a writer) rejects through `rejectProposal`; elsewhere the issue is a record, and the sync closes it as completed once a non-PR delivery lands (`issueClosed`). `takeIssues` skips `zero:propuesta` issues (`PROPOSAL_LABEL` lives in `keys.ts`). `src/intake/linear.ts`: Linear issues as requests for lines with `linear: { team, label }` (strict, no keys; the key is the secret `LINEAR_API_KEY`, read by the daemon's real factory, and without it `pollLinear` records a problem under `linearProblemKey`). Only issues created and labeled by active non-guest team members; per-issue kv `linear-issue:<team>/<id>` like GitHub's `IssueState` plus `completed`, so a failed move to a `completed` workflow state is retried without repeating the delivery comment. It reuses `report` from github.ts (`replyHere: false`: later comments are not read), signs every comment with `lineSignature` itself, and runs in its own daemon pass outside the GitHub meter (`DaemonOptions.linear` injects the adapter). `src/intake/jira.ts`: Jira Cloud issues as requests for lines with `jira: { site, project, label }` (strict, so no credential fits in the file; credentials are `JIRA_EMAIL` and `JIRA_API_TOKEN` from `SecretStore`). `pollJira` (its own daemon pass on the intake interval, outside the GitHub meter, awaited on exit) takes not-done labeled issues only when the creator, the last labeler and every summary/description editor in the changelog have `EDIT_ISSUES` (a failed check is a line problem, not a refusal), reports through `report` from `github.ts` with `replyHere: false` (it reads no Jira comments), signs with the line signature and moves delivered issues to a done-category status (`closeDone`; without a transition, `jira.problem.<line>` in kv until it can). State lives in kv `jira:<host>/<KEY>`; `jiraIssues` is the REST v2 adapter. `src/intake/security-alerts.ts`: Dependabot alerts as security jobs, for lines with `securityAlerts.mode` other than `off` (default `{ mode: jobs, minSeverity: high }`) whose remote is on GitHub. `pollSecurityAlerts` (the daemon's `readAlerts`, a background pass on the intake interval under the meter's `alerts` pass, off in `once` runs unless `DaemonOptions.alerts` is injected) reads the open alerts through `AlertApi.openAlerts`; in `jobs` mode new alerts at or above `minSeverity` with a fixed version become one `requestWork` job per package (ecosystem plus name; source `{kind: 'security-alert', repository, ecosystem, package, alerts, severity}`, target the highest `fixed`), or join that package's unfinished job. Each taken alert is kv `security-alert:<repo>#<n>` (never taken again), the line's open alerts kv `security-alerts:<line>` (the snapshot `securityAlerts` in `app.ts` gives `zero status` and the briefing) and a 403/404 or other read error kv `security-alerts.problem.<line>`; a GitHub limit rethrows and records nothing. `defaultPriority` in `src/priority.ts` makes the jobs of high and critical alerts `urgente` (the one priority zero gives on its own; `requestWork` still refuses it when asked for with a source) and the rest `media`; `requestBlock` frames them as Dependabot data. `src/intake/research.ts`: `syncResearchIssues` (run right after `syncProposalIssues` in the same daemon pass) publishes each research note once as a `zero:investigacion` issue, scrubbed with `scrubLocal` and with @mentions broken (`breakMentions`). `src/intake/inert-media.ts`: `inertMedia` (pure, no imports, no reading of context) escapes `![` as `!\[` and turns the `<` of `img`, `picture`, `source`, `video`, `audio` and `iframe` tags into `&lt;`, so opening an issue fetches nothing. It runs last, after `scrub` (which can bring the syntax together), on titles and bodies of notes and proposals and on the proposal comments of `syncProposalIssues`; replies from `reply` in `comments.ts` do not go through it. `webUrl` in `src/line/research.ts` keeps sources without query string or fragment. Data can still travel in a URL's path, and normal links remain.
- `src/github-quota.ts`: the factory's share of the account's GitHub quota. `githubMeter` (one per daemon) gives each pass (`merges`, `reverts`, `issues`, `proposals`, `research`, `scout`) an Octokit whose `request` hook refuses with `GithubHalted` during a pause, sends `If-None-Match` on GETs with a saved ETag (in memory, 500 entries; a 304 returns a `structuredClone` of the saved response, because pagination modifies what it receives), and keeps kv `github:quota` (only `core` or an unnamed resource), `github:halt` and `github:usage` (counts per pass for the current UTC hour). Inside the hook, options must change on the object it receives: the inner hooks are bound to it. `githubHalt` is the pause in force: a limit response (`isRateLimit`, until the later of `x-ratelimit-reset` and `retry-after`, or 60 s) or the 20% reserve while the quota is valid. The daemon starts no issue, proposal, research, merge or revert pass during one, and `endRun` logs each run's requests. `githubStatus` feeds the `GitHub:` line of `formatStatus`, shown at 40% or less or during a pause. `IssueApi.permission` rethrows limits instead of answering `none`. `src/tracker.ts` and the CLI stay outside the meter on purpose, so a finished job can still open its pull request.
- `src/panel/`: the control panel the daemon serves on 127.0.0.1. `server.ts` (session from the key in the link's fragment, Origin checks, actions through `app.ts`), `html.ts` (server-rendered pages in one `page()` layout: a CSS-only collapsible side menu (`NAV`, inline SVG icons, `#nav-toggle` checkbox, a dropdown on phones), the site's palette, fonts and logo in one inline `STYLE` with light and dark tokens, and shared status tokens behind `class="chip" data-status`; the production line view at `/line` is a board of eight lanes (the seven stations plus `out`) with compact job cards, which refreshes its cards from a fragment pushed on the `/line/events` stream, polling as a fallback, the job page's `Fundir` button for a delivered GitHub pull request not yet merged or closed (`/job/<id>/merge`, a confirmation page until `confirm=1`, then `mergePullRequest` with via `panel` and `PanelOptions.merges`, the daemon's metered real adapter), the read-only `/about` and `/agents` pages built from `factoryGuide` in `app.ts`, the `/proposals` tab built from `proposalsView` in `app.ts`, whose approve button only shows a confirmation page until the form carries `confirm=1`, the `/requests` tab ("Pedidos") built from `requestsView` in `app.ts` (typed form through `requestWork`'s `type`/`title`/`description`, `REQUEST_TYPES`; list with line and estado filters; answer, and stop behind a `confirm=1` page), and the `/research` tab built from `researchView`, whose "Pedir trabajo" button confirms the same way before `requestFromResearchNote`; the read-only `/monitor` tab built from `monitorView` in `app.ts`, filtered by `periodo` through `parsePeriod`, aggregates jobs, spans (`store.spansSinceAny`; tokens are `gen_ai.usage.*`, which the Claude engine reports through `EngineResult.tokens`), `budgetState` windows and `mergeKey` states without writing or asking GitHub), `charts.ts` (the monitor's gauges, bars and line chart as inline SVG), `key.ts` (key in the keychain), `tunnel.ts` (optional cloudflared quick tunnel, downloaded with consent and kept by the daemon).
- `site/install.sh` (POSIX sh) and `site/install.ps1` (ASCII, errors thrown instead of `exit` so `irm | iex` keeps the window): the one-step installer served by the site. They check Node 22+, npm and git without installing them, refuse an existing folder that is not a clone of the repo (a clone is updated with `pull --ff-only`), ask `[s/N]` (from /dev/tty on Unix) before cloning, `npm ci`, `npm run build` and writing the `zero` command in the user's folders (user PATH only on Windows), then launch `zero setup`. `test/installer.test.ts` checks them.
- `openspec/`: specs (`specs/`) and changes (`changes/`). `docs/adr/`: decisions.

## Conventions
- What the factory produces while working (reports, briefings, proposals, notes, traces, media, panel exports, `state.db`, logs, any file of ZERO_HOME) stays only in ZERO_HOME, and only development for a repository enters it. Zero enforces it (`operationArtifacts`, `allowedArtifacts` per line, `saveReport`), so new output goes under `FactoryHome`, never in a repository or the current folder.
- ESM, Node 22, imports with the `.js` suffix. What zero shows the owner (CLI, panel, chat) is in Spanish; code, comments and agent instructions are in English.
- What a person reads says "vos" or "you"; in the third person (documentation, the site, issues, the monthly report) it says "la persona responsable", "quien está a cargo" or "the person in charge". Internal names, configuration, agent instructions and tests may say owner. `test/wording.test.ts` checks it.
- The README is kept in both languages: English in `README.md` and Spanish in `README.es.md`, with the same structure and the same code blocks (`test/docs.test.ts` checks it). Every documentation change is made in both; what zero shows the owner (CLI, panel, chat) stays in Spanish.
- Engine-specific behaviour stays in `src/engines/`; nothing else may assume a vendor.
- Guarantees are enforced by zero, never trusted to an engine: read-only stations, timeouts, schema validation, verify gate, protected paths, citation checks, isolation box, egress gate.
- The chat may only tighten egress rules (block); allowing a site or changing the mode is for the owner on the terminal or in the file.
- Nothing installs software or needs admin without the owner's explicit consent. Secrets never go in argv, files or logs.
- The line never blocks on the owner: questions park a job, carry a timeout and a default answer, and approvals resume from a checkpoint.
- Every job end goes through `finalizeJob`, so it gets a final status, a closed job span and a townhall report.
- The townhall must never break production: store failures are logged, not thrown.
- Behaviour changes start as an OpenSpec change under `openspec/changes/`.
