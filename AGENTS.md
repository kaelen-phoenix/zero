# zero

A software factory that runs on its owner's machine. Agents of any vendor work on this repo, so keep this file accurate. `CLAUDE.md` only points here.

## Commands
- `npm run typecheck`: TypeScript, strict, including tests
- `npm test`: Vitest (`test/`); uses real git in temp repos and fake agents, never a model
- `npm run build`: compiles `src/` to `dist/` (the MCP server and the daemon run from `dist/cli.js`)
- `npx openspec validate --all`: specs and changes under `openspec/`

## Layout
- `src/cli.ts`: commands. `src/app.ts`: operations shared by the CLI, the MCP server and the daemon (request, status, answer, stop, briefing, trace). Never duplicate logic between interfaces; add it here.
- `src/config.ts`: `zero.factory.yaml` schema, effective level, `commitAuthor` (global and per line: `zero` or `owner`; with `owner`, `authorEnv` in `src/workspace.ts` passes the line repo's git config identity as GIT_AUTHOR_* to work-copy commits and merge-mode integration, zero stays the committer and is the author when no identity is configured). `src/signature.ts`: zero in the loop's signature (`signature` in the file, global or per line, resolved by `lineSignature`): `withTrailer` on every factory commit (spec, attempts, integration merge), `signText` on pull request bodies (`deliveryBody`), and `signedIssues`/`signedMerges`, with which the daemon wraps its real GitHub adapters per line (each pass hands its api factory the line), so issues and comments end with the text before FACTORY_MARK. `src/init.ts`: `zero init`, `zero line add`. `src/home.ts`: `ZERO_HOME` layout (`drills` holds the regeneration drills).
- Docker: `docker/Dockerfile`, `compose.yaml` (no socket, no credentials) and `docker/compose.box.yaml` (the only one mounting the socket, data at the same path inside and out); `docs/adr/0003-fabrica-en-docker.md` has the decisions. `ZERO_CONTAINER=1`, read only through `inContainer` in `src/home.ts`, changes three things. `SecretStore` (`src/keychain.ts`, `defaultKeyring`) stores in `secrets.enc` (`encryptedFileKeyring`, AES-256-GCM, key in `ZERO_MASTER_KEY_FILE`, by default the Docker secret `zero_master_key`, nothing written without a key that opens the file) and reads Docker secrets (`ZERO_SECRETS_DIR`) between the environment and the store. The daemon starts no jobs or idle passes while the box is not ready (`waitsForBox` in `app.ts`) instead of moving to local copies. Engines outside the box get their credential only in their own process (`EngineRequest.env`, `localCredentials` in `src/agent.ts`, given `secrets` by the daemon). `githubToken` also reads `GH_TOKEN` from the store, and `zero git-credential get` hands it to git for github.com. `panel.host` in the factory file (default 127.0.0.1) is where the panel listens.
- `src/setup.ts`: `zero setup` (`runSetup`, every terminal and machine access injected through `SetupDeps`): modes, engines (its `ENGINES` table holds each CLI's login and credentials), limits, isolation, panel and GitHub; it refuses without a terminal, installs nothing and writes through `initFactory` and `editFactory`, so it can run again.
- `src/budget.ts`: the single answer to "can the factory start more work?". Subscription plans are limited by their usage windows, read from each agent call's span (`quotaAttrs` in `src/agent.ts`); per-use billing by the dollar caps, each engine on its own, and for 15 minutes (`UNKNOWN_RESET_MS`) after a call refused because the API key ran out of credit (`Credit balance is too low`, marked `limited` by `claudeResult` and `claudeThrown` in `src/engines/claude.ts`). `pickEngine` chooses each call's engine from the station's chain (`stationChain` in `src/config.ts`: its engine, then the owner's `fallback` list); the factory pauses only when a line station has every engine of its chain paused. Engines report plan usage as `EngineResult.quota`.
- `src/state/store.ts`: SQLite state (jobs, spans, kv). `src/telemetry/`: tracer and the single definition of every metric; `otlp.ts` is the optional OTLP/HTTP JSON export (`telemetry.otlp` in the factory file, header values as secret names resolved through `SecretStore`), a daemon pass that sends finished jobs after a kv cursor (`otlp:cursor`), scrubs with `scrubLocal` and retries a batch at most 5 times.
- `src/line/`: the production line. `runner.ts` is the state machine (checkpoints, attempts, policy). Each station has a module (`spec`, `verify`, `review`, `integrate`); `security` reuses `review.ts` with its own instructions. Once a spec is valid and feasible, and before anything is written, `specStation` passes it through `uniqueRequirementNames` (`src/line/spec.ts`): a requirement name repeated in the request or in `existingRequirementNames` (the capability's main spec and other unarchived changes' deltas, compared like openspec's fold) gets the suffix ` (<job id>)`, then ` (<job id>-<n>)`, so `openspec archive` does not fail with `already exists` and no extra model call is spent. It only sees the work copy, so two unintegrated jobs can still repeat a name. `automerge.ts` merges pull requests of `autoMerge` lines once GitHub reports them ready (polled by the daemon); a blocked one keeps `backoff` in its `MergeState` and, with the same head and `mergeable`, is asked only for `pullRequest` until the wait (5 minutes doubling up to 60) ends. A pull request with `mergeable: false` goes back to the queue through `takeBack` when the job has a spec and attempts left, its local branch is at the head, that head was not tried (`MergeState.resolving`, kept by every write) and the base fetches; otherwise it is told as blocked. The kv mark `prRefreshKey` (`src/line/finish.ts`) drives the update: `runJob` runs `WorkCopy.mergeBase` on the base commit it pins in the mark (`baseCommit`, since `origin/<base>` is shared and moves during the job; a clean merge resumes at verify with no attempt spent; a conflict goes to build as an attempt, `buildLoop` restarting the merge from the head before every engine call and refusing what `conflictMarkers` finds or a branch without the base), checks again before integrating, and `integrate` with `existing` compares `ls-remote` with the head and pushes without force, opening nothing. With the mark, `finalizeJob` turns `failed` or `stopped` into `delivered` with the original delivery, moves the branch back to the head and posts a `blocker`. `policy.ts` is the only place that decides when the owner is asked. `finish.ts` is the only way a job ends. A passing network cut that reaches `runJob`'s final catch (`isTransientNetworkError`: ECONNRESET, ETIMEDOUT, EAI_AGAIN, ECONNREFUSED or EPIPE in the `code` or message of the error or its causes) puts the job back in the queue from its checkpoint, at most 2 times in its life (kv `network-retry:<job>`): uncommitted changes are dropped and a cut build does not spend an attempt. Anything that fails while first preparing the work copy (`SetupFailed`) is never retried, since a resumed job would skip setup. A 422 `already exists` when opening a pull request ends in `integration-blocked`.
- `src/line/verify.ts`: the verify station. `operationArtifacts` holds the shapes of the factory's operation output (added files only, minus the line's `allowedArtifacts` and the Markdown of the job's own specification), including regeneration drill output (everything under a `drills/<id>/` folder holding an added `informe.md` or `resultado.json`, and that pair added in the same folder anywhere, found over all added files, allowed ones included); `verifyChange` runs it before protected paths and commands, failing the attempt, and `runJob` runs it again over the whole change just before integrating, failing the job.
- `src/line/dependencies.ts`: the dependency check, off unless a line sets `checkDependencies`. After verify and before the reviewers, `buildLoop` runs `newNpmDependencies` (changed package.json and package-lock.json read with `git cat-file blob` at HEAD and at the merge base, up to `MAX_MANIFEST_BYTES`, a HEAD manifest that cannot be read or parsed counting as `unreadable` and reaching security as unverified; lock entries resolved outside `https://registry.npmjs.org/` and non-registry specs are left out) and `checkDependencies` (OSV querybatch and deps.dev from zero's process through `RunnerDeps.fetch`, 10 s per request). A `MAL-` advisory, a 404 on deps.dev or an invalid name fails the attempt; recent (under 7 days) or first versions and unverified packages (any request failure, never thrown) reach only the security prompt through `dependencyBlock`.
- `src/line/scout.ts`: the night shift. While the factory is idle (no queued or running jobs, andon off, budget left, inside the optional `nightShift.hours`), the daemon runs `scoutPass` in the background: the read-only `scout` station (`agents/scout.md`) looks at each line once per period (the day, or the window) and zero keeps only the proposals that pass `filterProposals` (no protected paths, no new credentials, no repeated titles, at most 3). On per-use billing the scout spends at most `limits.usdPerNight` per period. Proposals live in the `proposals` table of `state.db`. `approveProposal`/`rejectProposal` in `app.ts` decide them; approving opens a normal job with source `{kind: 'night-shift'}`. Each stored proposal gets `proposalAutonomy` (the line's `lineAutonomy`, restricted by `research.autonomy` for every proposal with a `researchNote`, whatever scout's `thirdParty` flag or its paths say; `proposalRequest` in `app.ts` states the note in the job's request as web data, not instructions). Under `build`/`auto`, and below `nightShift.maxAutoJobsPerDay` across lines (`autonomousJobsSince`), scout approves it itself: a job with source `{kind: 'night-shift', proposal, autonomy}` and the proposal's `decidedBy: 'night-shift'`. The runner parks `build` jobs (and `auto` research-born jobs whose diff touches a manifest, unless research is `auto`) at `before-integrate` with onTimeout `reject` (`nightShiftHold`); `approveProposal` then answers that job and `rejectProposal` stops it. The daemon considers owner jobs first (`ownerFirst`) and starts an autonomous job only when nothing else is queued or running. Rejections go to the line's townhall with the owner's reason, and scout's prompt lists the line's last 20 rejected or reverted proposals (`recentRejected`). Per line, `scoutIssues` lists through `IssueApi.unlabeled` the open unlabeled issues written by writers (TRUSTED) not yet linked by a proposal (at most 20, newest first) as data in scout's prompt; a proposal's `issue` is kept as `sourceIssue`/`sourceIssueUrl` only when it was listed. At the start of each `scoutPass` (after the off/hours and andon checks), `promotePending` takes on pending proposals of lines now at `build`/`auto` through `takeOnItsOwn` (oldest first, within `maxAutoJobsPerDay`), never third-party ones (`thirdParty` or `touchesManifest`). `ownerOnly` keeps a proposal at `propose` whatever the autonomy: born from a business note (`business`), flagged `commercial` by scout (license, pricing, charges, payments, legal text) or with paths matched by `touchesLegal` in `policy.ts`; `nightShiftHold` also holds any autonomous job whose changed files match `touchesLegal`. The briefing and the panel's Investigación tab split notes into "Negocio" and "Técnica".
- `src/line/reverts.ts`: `detectReverts` (a daemon pass on the intake interval) marks `reverted` the night-shift proposals whose job integrated on its own (no `approvals.integrate`; delivery mode `merge` with a commit, or `pull-request` with the merge or squash commit that `automerge.ts` or the pass itself records from GitHub's `mergeCommitSha`) once the base branch (local, or `<remote>/<base>` after a fetch on pull-request lines) has a `This reverts commit <sha>` commit or, for pull requests, GitHub's `Reverts owner/repo#N`, and posts a `propuesta revertida` lesson to the line's townhall. A pull request GitHub reports closed without merging is asked about again only 24 hours later (`reverts:closed:<job>` in kv, an ISO date), since it can be reopened and merged; the date goes when it is seen open or merged with a commit, and a store failure only means asking as usual. Errors from GitHub open no wait.
- `src/line/drill.ts`: the regeneration drill behind `zero simulacro <line> <capability> --archivos <glob>... [--usd N]` (`regenerationDrill` in `app.ts`, which refuses before creating anything: unknown line, `isolation: container`, andon, `budgetState` reached, `--usd` not positive or above `limits.usdPerJob`, no `verify`, no `openspec/specs/<capability>/spec.md` at the base branch, `<ZERO_HOME>/drills` inside a line's or the current folder's repository (`versionedAt`, shared with `saveReport`), no file left by `drillFiles`). `runDrill` clones the base branch with `--no-hardlinks --no-local` into `<ZERO_HOME>/drills/<id>/copy`, removes the matched tracked files (never tests, `isTestFile`, nor `openspec/`), replaces `.git` with a fresh one-commit repository, runs `setup`, makes one `build` call (`pickEngine`, `maxBudgetUsd`, `DrillOutput` with `missing`), runs `verify` (20 minutes each) and writes `informe.md` and `resultado.json` next to the copy. Outcome: `inválido` when a test or spec differs from the copy's commit, `alcanzan` when every file came back, verify passed and the agent ended ok without its cap, else `no alcanzan`.
- `src/line/research.ts`: the research station (`agents/research.md`, access `web`: on Claude the read tools plus `WebSearch`, elsewhere like `read`). While the factory is idle the daemon runs `researchPass` with the night shift's gates; only lines with a line-level research skill (`lines[].stations.research.skills`) research. Each (line, skill) pair runs once per local day (kv `research:<line>:<skill>`), with a prompt naming that single skill and at most `research.perLinePerDay` notes of its own, least recently researched first. Skills listed in `lines[].stations.research.business` (`businessSkills` in config.ts; names not in `skills` are ignored) write business notes (`skill`, `business` on the note). Notes (http(s) sources only, local paths scrubbed by `sanitizeNotes`) live in the `research_notes` table; scout's prompt gets its line's notes of the last 7 days as data. `scoutSpent` counts what scout, research and the packages' stations were really charged (`billedUsd` in `budget.ts`, like `jobBilledUsd`: subscription calls do not count, unknown billing does), since they share `limits.usdPerNight`; the daemon runs them one after the other in a single shared idle run (`idlePasses`: scout, then research, then the packages' stations), so each pass computes its cap after the other's spend is recorded. `requestFromResearchNote` in `app.ts` opens a job with source `{kind: 'research'}`. `research.autonomy` caps every research-born proposal (see `proposalAutonomy` in scout.ts); scout's output carries `researchNote` (kept only when it is one of the line's notes in the prompt) and `thirdParty`.
- `src/priority.ts` (pure): job priorities `baja`, `media`, `alta`, `urgente`, stored on the job (`priority` column; absent or legacy rows default through `defaultPriority`: `baja` for autonomous night-shift and package sources, else `media`). `effectivePriority` raises a queued job one level per full 24 hours (`PRIORITY_AGING_MS`) up to `alta`. The daemon orders queued jobs with `ownerFirst` (effective priority, then `createdAt`, stable), starts an effective `baja` only with nothing running and nothing higher queued, and runs at most one `urgente` at a time. `requestWork` refuses `urgente` with a `source` (only the owner) and unknown levels; `setPriority` in `app.ts` (`zero priority`) changes an unfinished job. Pausing running jobs for an urgent one is not implemented.
- `src/daemon.ts`: background loop; `runDaemon` takes the lock before touching any state and releases it last. `src/daemon-lock.ts`: the single-daemon guarantee, an operating system lock on `daemon.lock` in ZERO_HOME (`acquireDaemonLock`, an empty SQLite file held in `BEGIN EXCLUSIVE`, which dies with the process and is not inherited; `daemonLockHeld`, a read-only look). `ensureDaemon` launches nothing while it is held, `shutdownFactory` in `app.ts` waits up to 60 s for its release (`zero shutdown` exits 1 with the pid otherwise), and `daemonProcesses` lists daemon processes on the machine for `zero status` only, since it starts a process. `src/mcp/server.ts`: chat tools. `src/install.ts`: client registration.
- `src/shell.ts`: `resolveBin`, `spawnTarget` and `spawnGit` are the only way to start git and engines with a cwd in content zero does not trust: on Windows a spawn without a shell looks in its cwd before PATH (unless `NoDefaultCurrentDirectoryInExePath` is set in zero's own environment, which `test/windows-exec.test.ts` clears), so a bare name goes by the absolute path found in PATH's absolute entries, and one that is not found starts from `TRUSTED_CWD` and fails as any missing program. `sh` is out of scope: verify's commands already run the repository's code and go to the box.
- `src/agent.ts` + `src/engines/`: engine-agnostic agent runner and one adapter per engine. `EngineResult.model` is the model that answered when the engine reports it (Claude: the key of `modelUsage` with the highest cost); the runner records it as `gen_ai.response.model` and logs when it differs from the requested one. A CLI engine (`src/engines/cli.ts`) that exits 0 without text counts as a failure (`<engine> devolvió salida vacía` plus the end of stderr); codex is judged by its last message, not by stdout. `codex exec` runs with `--json`, so its stdout is JSONL: without the last-message file the answer is the last `agent_message` event, a failed exit tells stderr or else the last `error`/`turn.failed` message, and `codexQuota` reports the plan (a key in `CODEX_API_KEY` or `OPENAI_API_KEY` is `api`; otherwise `codex login status`, run from the engine's temporary folder after the call with a 10-second limit and whose failures change nothing, tells; the last valid `rate_limits` become the windows and imply `subscription` when the session says nothing; a failed call with a window used up is `limited`; a failed call whose stderr or last `error`/`turn.failed` message says `insufficient_quota` or `You exceeded your current quota`, outside a known subscription, is `api` and `limited`, through `codexOutOfCredit`, so the budget pauses codex for `UNKNOWN_RESET_MS`). `codex exec --output-schema` only takes OpenAI's strict mode, so `codexEngine` alone (`src/engines/codex-schema.ts`, pure) sends `toStrictSchema(req.schema)` (closed objects, every property required, optionals nullable through `anyOf` with null, an allowlist of keywords, nothing next to a `$ref`), answers `ok: false` without starting codex, naming the path, when a schema has no strict form (root not an object, dictionaries, free values, tuples, `allOf`), and sets `output` to the answer after `withoutOptionalNulls`, guided by the original schema; `text` keeps the raw message and other engines get the original schema. Above 30,000 characters of `fullPrompt`, `antigravityInvocation` sends the prompt on stdin and leaves a short instruction in `-p`, since the Windows command line stops at about 32K; custom engines keep their own way of receiving it. In `claudeOptions` (`src/engines/claude.ts`), `allowedTools` only auto-approves; on `read` and `web` access `disallowedTools` removes `Agent`, `Workflow`, `WebFetch`, `RemoteTrigger`, `CronCreate`, `ScheduleWakeup`, `SendMessage` and `PushNotification`, and `write` denies nothing. Tests use fake agents, so the final check is the tools in the `init` message of a real run. `agents/*.md` holds the per-station instructions, shared by every engine. `codex: { sandbox: off }` in the factory file (the owner's alone: no chat tool touches it) makes `resolveEngine` return `unsandboxedCodexEngine` (`--sandbox danger-full-access`, `-c approval_policy="never"`, `Engine.unsandboxed`), unless a custom engine is named codex; `BoxAgentRequest` does not carry the option, so inside the box Codex keeps its usual flags. `runHere` in `src/agent.ts` passes that engine's non-`write` calls through `runGuarded` (`src/readonly-guard.ts`): a snapshot in a temporary git repository of its own (no filters, nothing written in the folder or a containing repository; a folder is treated as a repository only if it is its root), plus raw HEAD, `config` and `hooks`, the real index and the references except `refs/remotes`. After the call it puts back only what differs, never `reset --hard` or `clean`, and fails the call keeping cost and quota; the temporary folder stays, named in the log, so what was discarded can be recovered. Anything else changing the folder or its checked-out branch during the call looks like the call's doing. Refs are the whole repository's, so `refChanges` only holds the call to its checkout's branch and, outside a linked worktree, the rest except `refs/heads/zero/*`, branches checked out elsewhere and new tags; those are logged, not rewound. Tracked files under an ignore rule are compared too (`trackedIgnored`). The daemon starts no job in a repository under a guarded call (`beingGuarded`) and a guarded pass call waits for the jobs running in its folder (`passExecute`). In `src/daemon.ts`, `passRunner` (issue replies, scout, research, the packages' stations) (through `passExecute`) sends unsandboxed engines to `BoxExecutor.execute` when the box is ready at that call, the rest to `runHere`; a job keeps its own runner, so a job in a local copy stays local. `formatStatus` warns through `FactoryStatus.codexUnsandboxed`.
- Custom agents: `agents` (global) and `lines[].agents` in the factory file (`CustomAgentSchema` in `src/config.ts`; fixed station names are reserved). `lineAgents` gives a line's agents in run order (global, then the line's); `customAgentChain` and `pickAgentEngine` (`src/budget.ts`) choose their engine; `stationEngines` (`src/box/credentials.ts`) includes them. `type` says what they do (`after` and `access` derive from it). `review`, the default: the runner runs them after review and security with `ReviewSchema`, as `AgentRequest.custom` (station `review`, access `read`, recorded under their own name); blocking agents' verified high/critical findings fail the attempt, informative ones only report. `build`: they write, in `buildLoop` after build and before verify, as `AgentRequest.custom` (station `build`, access `write`), with an optional `files` glob list matched against the change without the job's spec files (no match: a `zero.skipped` span, no call); zero commits their work with their name, `ok: false` discards it and fails the attempt, and a plan or budget cut resumes at the same agent (`job.station`). Both read their instructions from `line.repo` (line agents) or the factory folder (global agents), never from the work copy. `.zero/agents/<station>.md` in `line.repo` adds to a fixed station's instructions (`lineInstructions` in `src/agent.ts`). `agentList`/`addAgent`/`removeAgent` in `app.ts` back `zero agent list|add|remove` (`--tipo`, `--archivos`); `agentList` gives the real running order, and the panel's `/agents` line cards show it through `factoryGuide`.
- `src/packages.ts`: agent packages, a way to extend zero with third-party or own agents. `loadPackages` (never throws) reads `zero-package.yaml` (`ManifestSchema`, `PACKAGE_INTERFACE`) from each entry of `packages` in the factory file (a `path` or an `npm` name under `<ZERO_HOME>/packages/node_modules`) and `factoryConfig` sets the result on `config.loadedPackages`, which never comes from the file. A broken package stays out whole, as a problem in `factoryStatus`, `packageList` and once in the log (`warnOnce`). Its agents join `lineAgents` with origin `package`, after the file's global ones, with the entry's `engine` and `model`; its skills are `<package>:<skill>` in `availableSkills` (`src/skills.ts`), with no links in their folders (refused on load, left out of the staged copy by `stageSkills`). Stations load only with `allowCode: true` and a real folder outside the lines' repositories and `worktrees`/`jobs`. `src/line/packages.ts`: `packagesPass`, the last idle pass of the daemon, runs each station at most once per `everyMinutes`, importing its module and building its `ctx` (`StationContext`, interface 1); `ctx.runAgent` records `package:<package>/<station>`, which `scoutSpent` counts in `limits.usdPerNight`. A station whose manifest declares `requests: { perLinePerDay: N }` may call `ctx.requestJob({ line, text })`, which goes through `requestWork` with source `{kind: 'package', package, station}` and returns `{ id }` or, never throwing, `{ reason }` (pass ended, no `requests`, unknown line, andon, budget, quota in kv `package:<package>/<station>:requests:<line>` per local day, counted only once the job exists). The text is cleaned with `publicText` plus the station's secret values and cut to 4000 characters. `requestBlock` in the runner presents it to agents as a third party's data; it does the same, from `job.source` alone, for `night-shift` (drafted by scout, possibly with web material, even if approved) and `research` (built from a web note) jobs, so only owner requests say `The owner sent`. These jobs follow their line's level and integration without `nightShiftHold`; the daemon treats them as low priority (`lowPriority`, shared with the night shift's own jobs: after the others in `ownerFirst`, one at a time and only with nothing else queued or running). `scheduledPass` (same file; the daemon's `runSchedules`, a background pass on the intake interval, whatever the line is doing and not held up by the budget) runs the module's `scheduled(ctx, { at })` for each local time of a station's manifest `schedule`, at most once per local day (kv `package:<package>/<station>:schedule:<HH:MM>`, the day, marked before the call) and only within 2 hours of that time (`dueSlots`, oldest first, yesterday's included); the andon or a missing secret leaves the time unmarked. There `ctx.runAgent` throws synchronously, so it never reaches a model; the rest of `ctx` is the same as in `pass`. A station whose manifest declares `onDemand: true` can be asked for one extra `pass` (`requestStationRun` in `app.ts`, behind `zero package run <package>/<station>` and `zero_package_run`): it refuses with a reason (format, unknown or not loaded, no `onDemand`, already pending, andon, budget), otherwise records kv `stationOnDemandKey` (the request time); `packagesPass` then calls `pass(ctx, { onDemand: true })` under the usual gates without touching `stationLastKey` or also running the regular turn, clears the key right before the call (or when the module cannot run), and the daemon's `idlePasses` skips the `INTAKE_MS` throttle while one is pending (`onDemandPending`). A pending request shows, read-only, as `onDemandPendingSince` on `packageList`'s station view (`corrida a demanda pendiente desde HH:MM` in `zero package list`) and in `FactoryStatus.onDemand` (a `Corridas a demanda pendientes:` line in `formatStatus`). `jobOrigin` in `src/format.ts` is their label in status, panel and line view; the briefing has its own section and the monthly report's `originLabel` a case. `packageList`/`packageAdd`/`packageUpdate`/`packageRemove` in `app.ts` back `zero package`; every factory-file edit in `app.ts` goes through `editConfig`, which keeps `loadedPackages`.
- Packages from git: `src/package-source.ts` (pure, imported by `config.ts`) has `isGitSource`, checked before `looksLikePath`, and `parseGitSource`, which refuses credentials, protocols other than https and ssh and anything git could read as an option, in errors that never repeat the source. `src/package-install.ts`: `GitRunner` (the real one has no shell, stdin closed, `GIT_TERMINAL_PROMPT=0`, `GIT_ALLOW_PROTOCOL=https:ssh`), `findOnPath` and `runNpm`: git and npm start by absolute path, from absolute PATH entries only, with no shell and from a folder outside the package (`git -C`, `npm --prefix`, npm through `process.execPath` and `npm-cli.js`), since on Windows a bare name or cmd.exe would find a `git.exe` or `npm.cmd` planted in the package's folder; `npmCiArgs`, `lockProblem` (npm builds a git dependency by running its code, `--ignore-scripts` or not, so `package-lock.json` and `npm-shrinkwrap.json` may hold only https registry tarballs and local links: read by `folderLockProblem` when adding, on folder updates and in `realDependencies`, by `lockProblemAt` from the new commit while planning a git update, before confirmation and shutdown; `npmSpecProblem` judges a package from npm through a lock built in a throwaway folder, and `runNpm` sets `npm_config_allow_git=none`; since `npm ci` empties `node_modules` of the package and each workspace through links, the same two functions refuse, when there is a lock, a `node_modules` that is not a real folder, a link leaving the package, `workspaces` patterns that could leave it and lock paths outside it), `manifestAt`, `widening`, `cleanText` for third parties' text shown on a terminal, and the kv records: `package-update:<name>` (`{seen, at, error?}`) and `package-lock:<folder>` (the lock's hash). A git entry in the factory file is `{git, path, commit}`. `packageAdd` clones into a temporary folder inside `<ZERO_HOME>/packages/git`, checks manifest and fit there, shows the summary, asks through `confirm` (default no), renames to `packages/git/<name>`, runs `npm ci --omit=dev --ignore-scripts` if there is a lock and only then writes the entry. `packageUpdate` first only looks (guards in `gitFolderProblem`, fetch, commits, widening and confirmation; a commit whose manifest is not a regular file, `manifestNotAFile`, which `packageAdd` refuses too, or cannot be read through `manifestAt` stops there), then with something to apply calls `shutdown` once, runs each package's `ApplyUpdate` (git returns to the previous commit on any failure, including a manifest on disk that differs from the one judged) and `start` once, only when the status was `stopped`. `src/line/package-updates.ts`: `packageUpdatesPass`, a daemon pass that at most every 24 hours (kv `package-updates:last`) records `ls-remote` and `npm view` results without touching a package's folder (it asks `ls-remote` for `<ref>` and `<ref>^{}`, since git lists an annotated tag's peeled line only when asked by pattern; with no reference, for `HEAD`); `packageList` reads only what is on record.
- `src/skills.ts`: the owner's Claude Code skills (personal and plugin) assigned per agent (`stations.<agent>.skills`) and per line (`lines[].stations.<agent>.skills`): discovery, resolution, and the per-run staged copy (without `allowed-tools`) that the Claude engine loads as a local plugin, other engines get appended to their instructions, and the box mounts read-only at /skills. `agentSkills` in `app.ts` is the single read-only view (with each SKILL.md's short description) behind the panel's `/agents` cards and the chat's `zero_lines`; each agent span records `zero.skills` and `zero.skills.missing`.
- `src/townhall/`: collective memory and the owner briefing.
- `src/report.ts`: the monthly report per line (no model, no store writes, no daemon pass). `monthlyReport` in `app.ts` picks the lines and the month's finished jobs for `zero informe`, the panel's `/report` and `/report/export`, and `zero_monthly_report`; `report.ts` builds it (`reportText` cleans every stored text, on top of `scrubLocal`) and renders Markdown and standalone HTML. `saveReport` in `app.ts` is the only writer of a report file, for `zero informe --html` and `/report/export`: it writes to `<ZERO_HOME>/reports` and refuses when that folder falls inside a line's repository or the current folder's.
- `src/box/`: the isolation box. `runtime.ts` detects Podman/Docker, `status.ts` inspects and caches readiness, `image.ts` and `box/Dockerfile` build the image, `run.ts` holds every hardening flag, `executor.ts` routes shell commands and agents into the box, `agent.ts` is the entry point inside it, and `setup.ts` walks the per-platform plan with consent. `src/keychain.ts` stores credentials in the OS keychain.
- The egress gate: boxes run on an internal network with no DNS and leave only through zero's proxy. With Podman the network is made with `--disable-dns` (`networkCreateArgs` in `network.ts`): Podman's own name server resolves nothing outside on an internal network and the gate, started there, would take it for its resolver; a network an earlier version left with it is made again once only this factory's gate is on it. `src/box/egress.ts` holds the rules (pure), `gate.ts` is the proxy (runs in its own container via `gate-main.ts`), and `network.ts` starts it, issues one pass per box run and moves its records into `state.db`. Only `suspicious` refusals affect a job.
- `src/intake/github.ts`: GitHub issues as requests (polled by the daemon). Only issues written and labeled by people with write access; the issue hears back per job status. `src/intake/comments.ts` answers later comments from people with write access through the read-only `reply` station (no repository; zero computes where the change is), which may open a follow-up job or answer a waiting question. Factory comments carry `FACTORY_MARK`, since they are posted as the owner. Pull-request lines start each job from the remote's base (`startingBase` in the runner). `src/intake/proposals.ts` mirrors night-shift proposals as issues on every GitHub line, whether or not it takes issues: `syncProposalIssues` (its own daemon pass) publishes them with the label `zero:propuesta` (never the work label), scrubbing secrets and the owner's paths, and tells the issue once about a decision taken in the factory (approval: comment plus work label, recording the issue state first so the intake opens no second job; rejection: comment plus close). `deliveryBody` closes the proposal's issue. On proposals whose `proposalAutonomy` is `propose`, the sync also reads each issue (`IssueApi.issue`): the work label applied by a writer approves through `approveProposal`, closing it without the label (by a writer) rejects through `rejectProposal`; elsewhere the issue is a record, and the sync closes it as completed once a non-PR delivery lands (`issueClosed`). `takeIssues` skips `zero:propuesta` issues (`PROPOSAL_LABEL` lives in `keys.ts`). `src/intake/linear.ts`: Linear issues as requests for lines with `linear: { team, label }` (strict, no keys; the key is the secret `LINEAR_API_KEY`, read by the daemon's real factory, and without it `pollLinear` records a problem under `linearProblemKey`). Only issues created and labeled by active non-guest team members; per-issue kv `linear-issue:<team>/<id>` like GitHub's `IssueState` plus `completed`, so a failed move to a `completed` workflow state is retried without repeating the delivery comment. It reuses `report` from github.ts (`replyHere: false`: later comments are not read), signs every comment with `lineSignature` itself, and runs in its own daemon pass outside the GitHub meter (`DaemonOptions.linear` injects the adapter). `src/intake/research.ts`: `syncResearchIssues` (run right after `syncProposalIssues` in the same daemon pass) publishes each research note once as a `zero:investigacion` issue, scrubbed with `scrubLocal` and with @mentions broken (`breakMentions`). `src/intake/inert-media.ts`: `inertMedia` (pure, no imports, no reading of context) escapes `![` as `!\[` and turns the `<` of `img`, `picture`, `source`, `video`, `audio` and `iframe` tags into `&lt;`, so opening an issue fetches nothing. It runs last, after `scrub` (which can bring the syntax together), on titles and bodies of notes and proposals and on the proposal comments of `syncProposalIssues`; replies from `reply` in `comments.ts` do not go through it. `webUrl` in `src/line/research.ts` keeps sources without query string or fragment. Data can still travel in a URL's path, and normal links remain.
- `src/github-quota.ts`: the factory's share of the account's GitHub quota. `githubMeter` (one per daemon) gives each pass (`merges`, `reverts`, `issues`, `proposals`, `research`, `scout`) an Octokit whose `request` hook refuses with `GithubHalted` during a pause, sends `If-None-Match` on GETs with a saved ETag (in memory, 500 entries; a 304 returns a `structuredClone` of the saved response, because pagination modifies what it receives), and keeps kv `github:quota` (only `core` or an unnamed resource), `github:halt` and `github:usage` (counts per pass for the current UTC hour). Inside the hook, options must change on the object it receives: the inner hooks are bound to it. `githubHalt` is the pause in force: a limit response (`isRateLimit`, until the later of `x-ratelimit-reset` and `retry-after`, or 60 s) or the 20% reserve while the quota is valid. The daemon starts no issue, proposal, research, merge or revert pass during one, and `endRun` logs each run's requests. `githubStatus` feeds the `GitHub:` line of `formatStatus`, shown at 40% or less or during a pause. `IssueApi.permission` rethrows limits instead of answering `none`. `src/tracker.ts` and the CLI stay outside the meter on purpose, so a finished job can still open its pull request.
- `src/panel/`: the control panel the daemon serves on 127.0.0.1. `server.ts` (session from the key in the link's fragment, Origin checks, actions through `app.ts`), `html.ts` (server-rendered pages in one `page()` layout: a CSS-only collapsible side menu (`NAV`, inline SVG icons, `#nav-toggle` checkbox, a dropdown on phones), the site's palette, fonts and logo in one inline `STYLE` with light and dark tokens, and shared status tokens behind `class="chip" data-status`; the production line view at `/line` is a board of eight lanes (the seven stations plus `out`) with compact job cards, which refreshes its cards from a fragment pushed on the `/line/events` stream, polling as a fallback, the read-only `/about` and `/agents` pages built from `factoryGuide` in `app.ts`, the `/proposals` tab built from `proposalsView` in `app.ts`, whose approve button only shows a confirmation page until the form carries `confirm=1`, and the `/research` tab built from `researchView`, whose "Pedir trabajo" button confirms the same way before `requestFromResearchNote`; the read-only `/monitor` tab built from `monitorView` in `app.ts`, filtered by `periodo` through `parsePeriod`, aggregates jobs, spans (`store.spansSinceAny`; tokens are `gen_ai.usage.*`, which the Claude engine reports through `EngineResult.tokens`), `budgetState` windows and `mergeKey` states without writing or asking GitHub), `charts.ts` (the monitor's gauges, bars and line chart as inline SVG), `key.ts` (key in the keychain), `tunnel.ts` (optional cloudflared quick tunnel, downloaded with consent and kept by the daemon).
- `site/install.sh` (POSIX sh) and `site/install.ps1` (ASCII, errors thrown instead of `exit` so `irm | iex` keeps the window): the one-step installer served by the site. They check Node 22+, npm and git without installing them, refuse an existing folder that is not a clone of the repo (a clone is updated with `pull --ff-only`), ask `[s/N]` (from /dev/tty on Unix) before cloning, `npm ci`, `npm run build` and writing the `zero` command in the user's folders (user PATH only on Windows), then launch `zero setup`. `test/installer.test.ts` checks them.
- `openspec/`: specs (`specs/`) and changes (`changes/`). `docs/adr/`: decisions.

## Conventions
- What the factory produces while working (reports, briefings, proposals, notes, traces, media, panel exports, `state.db`, logs, any file of ZERO_HOME) stays only in ZERO_HOME, and only development for a repository enters it. Zero enforces it (`operationArtifacts`, `allowedArtifacts` per line, `saveReport`), so new output goes under `FactoryHome`, never in a repository or the current folder.
- ESM, Node 22, imports with the `.js` suffix. What zero shows the owner (CLI, panel, chat) is in Spanish; code, comments and agent instructions are in English.
- What a person reads says "vos" or "you"; in the third person (documentation, the site, issues, the monthly report) it says "la persona responsable", "quien está a cargo" or "the person in charge". Internal names, configuration, agent instructions and tests may say owner. `test/wording.test.ts` checks it.
- The README is kept in both languages: English in `README.md` and Spanish in `README.es.md`, with the same structure and the same code blocks (`test/docs.test.ts` checks it). Every documentation change is made in both; what zero shows the owner (CLI, panel, chat) stays in Spanish.
- Engine-specific behaviour stays in `src/engines/`; nothing else may assume a vendor.
- Guarantees are enforced by zero, never trusted to an engine: read-only stations, timeouts, schema validation, verify gate, protected paths, citation checks, isolation box, egress gate.
- The chat may only tighten egress rules (block); allowing a site or changing the mode is for the owner on the terminal or in the file.
- Nothing installs software or needs admin without the owner's explicit consent. Secrets never go in argv, files or logs.
- The line never blocks on the owner: questions park a job, carry a timeout and a default answer, and approvals resume from a checkpoint.
- Every job end goes through `finalizeJob`, so it gets a final status, a closed job span and a townhall report.
- The townhall must never break production: store failures are logged, not thrown.
- Behaviour changes start as an OpenSpec change under `openspec/changes/`.
